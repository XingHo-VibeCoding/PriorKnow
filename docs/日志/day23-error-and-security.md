## 二、① 密钥排查（红线，先做）

### 2.1 跑了什么

```bash
# 工作区（只看被版本管理的文件）
git grep -n -I -i -E "password|passwd|secret|sk-[a-zA-Z0-9]{8,}|postgres://|postgresql://|AKID|api[_-]?key|access[_-]?token|BEGIN [A-Z ]*PRIVATE KEY" \
  -- . ':(exclude)*.lock' ':(exclude)package-lock.json'

# 全部 Git 历史（61 个提交，所有分支/标签可达的）
git grep -n -I -i -E "password|passwd|secret|sk-[a-zA-Z0-9]{8,}|postgres://|postgresql://|AKID|api[_-]?key|access[_-]?token|BEGIN [A-Z ]*PRIVATE KEY" \
  $(git rev-list --all) -- . ':(exclude)*.lock' ':(exclude)package-lock.json'

# 补充：高熵串（像密钥的长 base64），源码里不该出现 40 位以上的连续 base64
git grep -n -I -E "[A-Za-z0-9+/]{40,}={0,2}" -- '*.js' '*.ts' '*.tsx' '*.json' \
  ':(exclude)**/package-lock.json' ':(exclude)**/*.lock'
```

### 2.2 结果

**高熵串：0 命中。**（排除 `package-lock.json` 之后一条都没有）

**特征词：6 处命中，全部是规则文本本身，没有一处是真值。** 逐条说明：

| 文件 | 行 | 内容 | 判定 |
|---|---|---|---|
| `.gitignore` | 11 | `secrets.json` | 忽略规则，不是密钥 |
| `docs/日志/day14-week2-validation.md` | 117 | 「全文搜索 `password\|token\|secret\|api_key` 仅命中 3 处，**全部是规则文本本身**」 | 记录上次排查的结论 |
| `docs/日志/day21-week3-validation.md` | 148 | 同上，第 3 周复检记录 | 同上 |
| `docs/日志/day21-week3-validation.md` | 206 | 复盘表格里「先按 `pg` 直连找『主机 / 端口 / 账号 / 密码』」 | 描述**找过但没找到**这件事 |

Git 全历史（61 个提交）的命中与工作区**完全同形** —— 因为这几行从写进去那天起就没改过，
没有「提交过又删掉」的历史残留。

### 2.3 为什么这个项目天然不容易漏

不是运气好，是架构上把「可泄漏的东西」消掉了：

- **零环境变量**。云函数连数据库走 `app.rdb()`，凭证由运行角色的 `getClientCredential()` 在运行时提供 —— 没有连接串、没有账号密码，代码里就没有可写死的值。
- **没有 `.env` 文件**，也没有过。
- **前端不持有任何凭证**。前端只会带一个 `X-User-Id`（不是密钥，是自报的身份，见第六节）。
- 仓库是 **Public** —— 所以这一条怎么强调都不过分，任何一次疏忽都是立刻公开的。

### 2.4 一条容易误判的：`package-lock.json` 里的哈希不是密钥

第一次扫高熵串时命中了 `app/package-lock.json` 上百条
`"integrity": "sha512-rDS5/31E9HfPl/..."`。

这是 npm 的 **SRI 校验和**，用于确认依赖包内容没被篡改，**不是密钥**：
它由包内容单向算出，公开在 npm registry 上，任何人都能看到。
把它当密钥删掉，只会让 `npm ci` 报错。

> 记在这里是因为**下次还会有人扫到它**。判据：出现位置是 `integrity` 字段 → 忽略。

### 3.2 用 `git check-ignore` 证明它真的生效（不是「写了就算」）

```
$ git check-ignore -v .env .env.local .env.production secrets.json app/certs/a.pem app/certs/a.key
.gitignore:5:.env	.env
.gitignore:6:.env.*	.env.local

```

`-v` 输出的第一列是**命中的那一条规则和它的行号** —— 这才叫证明。
只看「文件没出现在 `git status` 里」是不够的：它可能只是恰好没被创建。

### 3.3 新增 `.env.example`

原先没有这个文件，因为项目**真的一个环境变量都不需要**。

那为什么还要加？因为它现在的作用是**反过来的**：它是一份「需要哪些变量」的声明，
而这份声明的内容是「零」。文件里写清了三件事：

1. 为什么不需要（`app.rdb()` 走运行角色，没有连接串）；
2. 将来真要加时按什么步骤加（本地 `.env` / 云函数控制台环境变量，绝不进 `cloudbaserc.json`）；
3. **前端 `VITE_` 开头的变量一律不算秘密** —— 任何人按 F12 都能看到。

第 3 条是真正有用的那一句：很多「密钥泄漏」不是提交错了地方，
而是**把只该待在服务端的东西放进了前端构建**。

## 四、③ 三类错误提示统一

### 4.1 改之前是什么样

「把异常变成一句话」这件事散在 6 个地方，写法都是：

```ts
'某某失败：' + describeError(err)      // 而 describeError 只是 error.message
```

问题在于 `message` 是**谁抛的谁写的**：

- 我们自己的校验（`任务内容不能为空`）→ 中文，能看懂；
- 浏览器 / IndexedDB 抛的 → **英文**。

于是最难看的一种是这样：写库时超配额，用户看到 **「保存失败：QuotaExceededError」** ——
既不知道发生了什么，也不知道接下来做什么。

更要紧的是，三类失败**该告诉用户的事完全不同**：

| 类别 | 用户需要知道的 | 一句「操作失败」说了什么 |
|---|---|---|
| 输入错 | 改哪一个字 | 什么都没说 |
| 网络错 | 先查地址还是先查网 | 什么都没说 |
| 服务端错 | 服务器说了什么（不要翻译） | 什么都没说 |

### 4.2 改成了什么

新增三个东西，把「分类 / 文案 / 排版」拆开：

| 文件 | 职责 | 为什么在这个位置 |
|---|---|---|
| `app/src/data/errors.ts` | `ValidationError` 类型 | **类型住在抛它的那一层**。数据层抛的错，类就该在数据层 —— 否则数据层要反过来 import 界面层 |
| `app/src/ui/errors.ts` | `explainError()` 分类 + 生成人话 | **解释住在读它的那一层**。只有界面层知道要显示给谁看 |
| `app/src/ui/ErrorNote.tsx` | 「标签 + 一句话」的排版 | 只管展示，不含判断；CloudSyncPanel 那种已经 catch 过的地方可以直接复用 |

五类，不是三类：

| kind | 标签 | 什么时候 | 文案示例（真实输出） |
|---|---|---|---|
| `input` | 输入问题 | 校验不过 | 标题不能为空 —— 这是唯一的必填项 |
| `network` | 网络问题 | `fetch` 直接 reject（`status===0`） | 连不上接口 —— 确认地址正确、这台设备能上网，再打开浏览器控制台看有没有跨域报错 |
| `server` | 服务端问题 | 服务器回了 4xx / 5xx | 服务端拒绝了这次请求（HTTP 400）：X-User-Id 格式不对（只能 1–64 位字母、数字、下划线或连字符） |
| `local` | 本机数据 | IndexedDB 抛错、或数据层说「任务不存在」 | 浏览器分给这个站点的存储空间满了。先「导出 JSON」备份，再删掉一些不用的任务，然后重试。 |
| `unknown` | 未预料的问题 | 剩下的一切 | 出错了，原因不在前面几类里（x is not a function）。刷新页面再试；反复出现就把这句话截图反馈。 |

**为什么多出后两类**：把「存储满了」硬塞进「你输入错了」是**说错话**，
比不说更糟 —— 用户会去改输入，而真正该做的是导出备份再删几条。
`unknown` 同理：这类要用户反馈，标签得让它一眼看出「这不是我操作错的」。

### 4.3 判断顺序（不能换）

```
① SyncError        → 它自己知道是网络还是服务端，别再猜
② 存储错误名        → DOMException.name 是标准值，可靠
③ ValidationError  → 我们自己抛的，天然是「输入问题」
④ 其他中文 Error    → 本机数据层的问题（如「任务不存在」）
⑤ 剩下一律 unknown  → 英文原文不直接给用户看，但也不吞掉
```

🔴 关键的一条：**不能只看 HTTP 状态码就分类**。`SyncError` 的 `status === 0` 覆盖了两种完全不同的情况 ——
「连不上」（网络）和「地址/编号没填」（其实是输入）。两者都说「检查网络」，
用户会去重启路由器，而真正该做的是把地址填上。所以 `status === 0` 还要再看一眼 message。

### 4.5 同一件事，用户视角的前后对比（评审看这一张）

上一张表是「改了哪些文件」，这张是「用户看到什么变了」。
五类的触发场景都是**真路径**，不是造出来演的。

| 类别 | 怎么触发的 | 改之前界面上是什么 | 改之后界面上是什么 |
|---|---|---|---|
| **输入问题** | 不填标题就点「加入队列」 | `标题不能为空 —— 这是唯一的必填项`（没有任何类别标注，和下面那种「未知问题」长得一模一样） | `[输入问题]` + 同一句话 |
| **网络问题** | 接口地址填 `https://no-such-host.invalid/api` | `同步失败：Failed to fetch` | `[网络问题]` + `连不上接口 —— 确认地址正确、这台设备能上网，再打开浏览器控制台看有没有跨域报错` |
| **服务端问题** | 用户编号填 `demo.user.001`（服务端点号被正则拒） | `同步失败：服务端拒绝了这次请求（HTTP 400）…`，前缀和后缀是手工拼的 | `[服务端问题]` + `服务端拒绝了这次请求（HTTP 400）：X-User-Id 格式不对（只能 1–64 位字母、数字、下划线或连字符）` |
| **本机数据** | IndexedDB 配额满 / 库版本旧 | `保存失败：QuotaExceededError`（浏览器给这类异常的 message 有时是空的，于是冒号后面**什么都没有**） | `[本机数据]` + `浏览器分给这个站点的存储空间满了。先「导出 JSON」备份，再删掉一些不用的任务，然后重试。` |
| **未预料的问题** | 代码 bug，例如 `x is not a function` | `保存失败：x is not a function` | `[未预料的问题]` + `出错了，原因不在前面几类里（x is not a function）。刷新页面再试；反复出现就把这句话截图反馈。` |

**这张表要证明的东西只有一句**：一个不懂技术的用户，看到任何一条报错都能知道
「是我的错 / 是网的错 / 是服务器的错 / 是浏览器存不下 / 该找谁」——
而不是对着一句英文一脸茫然，不知道该改哪儿、该找谁、该不该重试。

所以每一类的文案都写成了「**结论 + 下一步**」两段，而不是只报「失败」：

| 类别 | 结论 | 下一步 |
|---|---|---|
| 输入问题 | 这个字段不行 | 改哪一个字（标题是唯一必填） |
| 网络问题 | 请求没发出去 / 没回来 | 先查地址，再查网，最后看控制台有没有跨域 |
| 服务端问题 | 收到请求了，服务器说不行 | 把服务器那句原话摆出来，不翻译 |
| 本机数据 | 浏览器这边的存储出问题 | 导出备份 → 删几条 → 重试（配额满）；刷新（库版本旧） |
| 未预料的问题 | 不是你的问题，是我们的 bug | 刷新再试；反复出现就截图反馈 |

> 一句话记法：**报错不是给开发者看的日志，是给用户看的「下一步」。**
> 所以判据不是「信息全不全」，而是「用户读完知道该干什么吗」。

### 4.6 顺带修掉的两处「一句话两个冒号」

改完第一版跑页面验证时抓到的：

- 原先：`同步：连不上接口：确认地址正确…` ← 前缀 + 服务端文案自带冒号，叠成两个
- 现在：`连不上接口 —— 确认地址正确…`（云端文案改用破折号；CloudSyncPanel 也不再补「同步」前缀 —— 标签已经说了是哪一类，卡片本身就在说同步）

### 4.7 服务端 5xx：文案只在一个地方定义

原先「服务器内部错误，请稍后再试」硬编码在 **3 处**（GET 的 catch、写入链路的 catch、DELETE 的 catch）。
今天新增了入口层的最后一道网，眼看要变成第 4 处，于是收口成 `cloudfunctions/api-health/messages.js` 里的一个常量。

分工写清楚了：

- **服务端**说「发生了什么」：`服务器内部错误，请稍后再试`
- **前端**说「该怎么反应」：`…（HTTP 500）—— 不是你操作的问题。`

前端那句必须由前端说：只有它知道这次是 5xx 而不是 4xx，能说得有依据；
服务端不知道调用方是谁、界面长什么样。
反过来，服务端也不该写「不是你填错了」—— 那样会出现「服务器内部错误，请稍后再试 ——
不是你填错了，稍等一会儿再试」，一句话里劝两遍。

### 4.8 入口层的最后一道网

业务层的 `try/catch` 只覆盖「进了 handler 之后」。**路由匹配、读请求头、拼响应、OPTIONS 分支**
原来没有任何兜底 —— 一旦在那里抛出，异常交给运行时，回给浏览器的就不是 `{ok,data,error}` 了。

后果不只是难看：前端的 `isEnvelope()` 判否 → 显示「接口返回的不是预期格式，
常见原因：地址少了 /api」—— 把「服务端炸了」说成「你地址填错了」，**恰好指错方向**。

这份兜底平时跑不到，所以专门写了一个脚本用会抛错的 `httpContext` getter 把它逼出来。

### 5.2 单元验证为什么必要

`verify-day23-errors.cjs` 直接 esbuild 打包 `app/src/ui/errors.ts` 再 `require` ——
验的是**真代码**，不是抄一份逻辑来测（抄的那份永远和线上一致，因为它是假的）。


最后一条尤其重要：**报错路径上再报错**，用户看到的就是白屏。

### 5.3 页面验证的断言里有一条特别的

```js
const RAW_PATTERNS = [/[A-Za-z]*Error\b/, /\[object \w+\]/, /\bundefined\b/, /\bNaN\b/, /TypeError|DOMException|QuotaExceeded/]
```

每条错误提示都要过这一关。不能简单用「含 ASCII 字母」判 —— 正常文案里也有 `HTTP`、`JSON`、`API`。

- 输入错 → 直接点「加入队列」不填标题；

> 而这三类错误随手一操作就能真实发生 —— 再造个开关就是演，不是验。

### 关于第 9 条（依赖漏洞）—— 今天为什么不动

```
zod              [high]      ← koa-body 的依赖
undici           [high]
systeminformation[high]
lodash.set       [high]  需手动(breaking)
koa-body         [high]      ← functions-framework 的依赖
axios            [high]  需手动(breaking)
@cloudbase/node-sdk        [high]  需手动(breaking)
@cloudbase/functions-framework [high]  **无修复**
@cloudbase/database        [high]  需手动(breaking)
fast-uri / lodash.unset / qs / uuid  [moderate]
```

三个判断：

1. **绝大多数不在我们的代码里**。`zod` / `koa-body` / `axios` / `systeminformation` / `undici`
   我们一行都没直接 import —— 它们躺在 CloudBase 官方 SDK 和框架的依赖树里。
2. **可达性低**。这些漏洞的触发点（文件上传解析、SSRF、URL 路径构造、系统信息查询）
   本项目一条都没用到：只有一个云函数、4 个路由、没有上传、没有出站请求、不渲染 HTML。
3. **修它的代价不成比例**。`@cloudbase/functions-framework` 标的是「无修复」，
   能修的几条都在 breaking 区。动它 = 换掉云函数运行时依赖 → 必须重新部署 + 重跑全部回归 +
   重做公网验证，而今天是结营前的倒数第 5 天。

**处置**：记在这里，等下次部署窗口一起处理。
真正能降风险的不是升级依赖，是第 1 条 —— 把认证做上。
