# 换用户编号：本机一本账 vs 云端分区（追加需求 `day24c`）

> 起因是他的一句复现：「换了用户编号再拉取，之前的用户数据还在。」
> 查下去发现这句话底下压着 **三个 bug**，其中两个他还没遇到、但后果更重。
> 本文只记「为什么这么改」，代码意图都写在对应文件的注释里。

---

## 一、三个 bug

| # | 现象 | 后果 | 谁发现的 |
| --- | --- | --- | --- |
| 1 | 换号后拉取，上一个号的任务还在列表里 | 两个账号混成一张表，**再也分不开**（本机没有 `user_id` 列） | 他 |
| 2 | 换号后点「推送本机任务」，会把任务整批写进新号名下 | **污染对方账号**。而且推完界面上还显示成功 | 我 |
| 3 | 游标全局只存一个（`priorknow-sync-cursor`） | 换号后拿 A 的 seq 去问 B，B 那边**序号更小的记录永远拉不到，且不报错** | 我 |

第 3 条最阴：它不会报错，界面还会显示「拉到 0 条变化 · 新游标 7」——
用户以为同步完成了，其实少了一半数据。

---

## 二、矛盾的根：本机一本账，云端按用户分区

- 云端：`tasks` 表有 `user_id`，每个接口都按它过滤（`WHERE user_id = ?`）。
- 本机：`tasks` 表**没有** `user_id` 列（IndexedDB schema 就 `'id, status, dueAt, importance, createdAt'`）。

这不是疏忽 —— 本机库从第 1 周就是「一个人的账本」，那时还没有账号这个概念。
所以「换号」在本机这件事上**没有中间状态**：要么这本账是 A 的，要么是 B 的，不可能同时是两个人的。

于是只有两条路：
- 给本机表加 `user_id`、所有查询带过滤（改动大，且 Dexie 要升版本迁移）；
- **或者**：认下「一本账」，换号就必须先把账清出去。

选了后者。理由：这本账的定位本来就是「当前用户的本机缓存」，不是多租户数据库。
真要支持两个账号来回切不丢数据，那是账号系统的事（登录上线后由认证决定身份，而不是文本框）。

## 三、改了什么

### 1. 游标按用户分开存

```ts
const CURSOR_PREFIX = 'priorknow-sync-cursor:'
loadCursor(userId) / saveCursor(userId, n)   // key = 前缀 + 用户编号
```

🔴 旧的那个不分用户的键**不做迁移**。换号后一律从 0 开始，代价是一次全量重拉；
全量重拉是幂等的（按 id 覆盖），比「猜一个游标」安全得多。

### 2. 记住「本机这批数据属于谁」

```ts
const OWNER_KEY = 'priorknow-owner'
loadOwner() / saveOwner(userId)
```

- 推送或拉取**成功后**才认领（失败的东西不该被认领）；
- `owner !== 当前编号` 就是那个必须先处理的状态。

### 3. 换号时拦住，并给一条出路

「云端同步」卡里出现一个虚线警示块，**标题点名两个号**：

> 本机数据属于「A」，不是「B」
> 这台设备只有一本账。现在点推送，会把「A」的 12 件任务写到「B」名下；现在点拉取，两个号的任务会混成一张列表 —— **之后再也分不开**。

下面是唯一的出路：`清空本机 12 件，切换到「B」`。三个按钮（推送 / 拉取 / 自检）同时禁用。

🔴 **不做成「点下去才报错」**：这里的错不是失败，是「会把数据写错地方」。失败可以重试，写错地方要收拾很久。
🔴 **不做自动清空**：清数据必须用户点头。确认框里写明「云端两边都不动，换回去再拉就能回来」——
    不说这一句，用户会以为按一下就全没了，于是宁可不点、继续混着用。

### 4. 「数据与设置」加清空入口

`清空本机 N 件任务`（带条数，库空时禁用）。换号那张卡是「被拦住时」的出口，
这个是「随时想清就清」的入口，两处都要有。

🔴 **清任务与游标归零必须一起做**。只清任务不归零，下次拉取从旧游标开始，
云端早期的记录永远拉不回来 —— 而界面上看起来一切正常。这是本次最难发现的一处。

### 5. 数据层补 `clearAll()`

```ts
clearAll(): Promise<number>   // 返回删了几条
```

不用 `importAll([])`：它也能清空，但语义是「导入一个空文件」，还会跑一遍规范化校验。
换用户这件事需要一个**说得出口**的方法名，调用处才读得懂自己在干什么。

## 四、验证时撞到的第三个坑：示例数据 id 撞号

改完后第一次线上跑「A 推 7 件示例」，7 件全被拒：

```json
{ "index": 0, "field": "id", "reason": "找不到这个任务（编号 sample-01）", "code": "NOT_FOUND" }
```

根因不是这次的改动，是**早就埋着的**：示例数据的 id 写死成 `sample-01`…`07`，
而 `id` 在云端是**全局主键**（不是「每个用户的第 01 号」）。
第一个把示例推上去的人就占住了这 7 个编号，第二个人推就撞「别人的行在本区不存在」→ 404 语义 → 整批被拒。

记忆里一直有一条「跨区测试前先 `DELETE … WHERE user_id='…'`」——
那是在**绕**它，不是在修它。而演示时正好会踩：载入示例 → 推上去 → 全红。

改法：`buildSampleTasks()` 给 7 条加同一个随机后缀（`sample-01-k3f9a2`）。
排序不受影响 —— 示例的 `createdAt` 已经互相错开一分钟，`compareEntries` 在第 3 步就分出先后，
永远走不到第 4 步的 id 兜底。

## 八、第二轮：「手动把所有任务删除后，推送后的数据啥也没有？」

他接着报的这句。先实测三件事，结果和直觉不一样：

| 我实测的 | 结果 |
| --- | --- |
| 删一条 → 云端那一条 | `deleted_at` 有值（**软删同步成功**，Day 22 那条 DELETE 通路是通的） |
| 删光之后点「推送本机任务」 | 红字「**输入问题**：本机没有任务可推。**在下面「云端同步」里补上再点**」 |
| 删光之后点「按游标拉取」 | 拉到 1 条变化（就是那条墓碑）→ 队列仍空，**没有复活** |

所以功能是对的，错的是那句话：**人就在「云端同步」这张卡里，却被指去「下面」**；
而且这是正常状态，却贴了「输入问题」标签、染成红字 —— 一句本地判断不该走错误通道。

但它同时暴露了一个**真缺口**：**没配接口地址时删掉的任务，永远推不上去。**
那条 DELETE 根本发不出去（`activeConfig()` 为 null 时只删本机），
于是本机空了、云端还满着，之后点推送只会得到那句话，而下次拉取会把它们全部「复活」。

### 改了三处

1. **空库推送不再报错**，改成中性的一句话（绿色），并回答他真正的问题：
   > 本机没有任务，也没有待补发的删除 —— 没有东西要推。删除是在你点「删除」的那一刻就同步的，不需要事后补推。

2. **离线删除留欠条**：`priorknow-pending-deletes` 记下这些 id，
   下次推送时逐条补发 DELETE。三种结果分别对待：
   - 成功 → 从欠条移除，报「补发 N 条离线时的删除」；
   - **404**（云端本来就没这条）→ 也算还清，但要**说出来**：「另有 N 条云端本来就没有，已从待补发清单里去掉」——
     悄悄吞掉比说错更糟；
   - 其他错误（断网 / 5xx）→ 留着下次再补，**不能因为一条失败把整批欠条丢掉**。
   换账（清空本机）时一并清空欠条：那不是「逐条删除」，是整本账不要了。

3. **`activeConfig()` 加 owner 判断**：本机数据属于别的号时返回 null。
   否则换号后点删除，DELETE 会打到新号的区里 —— 那边没这个 id，回 404，
   界面只会说「删除失败」，而真正该做的是先清账。

### 验证

- `_pending-delete-check2.mjs` **13 项全过**（线上真账号）：先推 7 条 → 清空地址模拟离线 →
  离线删 1 条留下欠条 → 重新配好 → 推送报「补发 1 条」→ 云端 7 行里那 1 条 `deleted_at` 非空，
  **且删掉的正是那条** → 拉取回来仍是 6 条，没复活 → 删光后推送给的是中性提示、不贴标签。
- `_owner-public-e2e.mjs` 回归 **14 项全过**（换号那条链路没被打坏）。
- 测试账号 `e2e-*` 全部 `DELETE`，库里只剩他的真实数据。

### 没做的一条（刻意）

**「本机空 ⇒ 推送把云端也清空」** 不做。那是「以本机为准整体覆盖云端」，
一台设备误操作就能把别的设备的数据全部抹掉，代价太大。
现在的语义是：删除在点删除那一刻同步；当时没法同步的，留欠条事后补 —— 没有第二种解释。

## 九、他指定的三种情况联测 —— 揪出「本地清空后拉不回来」的真原因

他要求一次验三件事：
①本地清空了，云端数据能不能覆盖本地；②云端加一个减一个，本地空白能不能正确拉取；
③本地加一个删一个，云端能不能正确保存。

**第一次跑，情况 2 挂了，而且它把情况 1 也拖下水：**

```
【情况 1】清空 → 拉取 → 拉回 7 条 ✅
【情况 2】云端加 1 删 1 → 清空 → 拉取 → 只拉回 1 条 ❌（应为 7 条）
```

差别只有一处：**情况 1 之前从没拉取过（游标是 0），情况 2 之前拉过一次（游标 246）**。

### 根因：游标是跨卡片的共享状态，但被当成某一张卡的私有变量

游标写在 localStorage，可**写它的有三个地方**：
拉取推进（云端同步卡）、清空本机归零（数据与设置卡）、换用户编号换位置（同步卡）。

而「云端同步」卡把游标缓存在自己的 `useState` 里，既用于显示也用于请求：

```
本机拉过一次 → 游标 246
去「数据与设置」清空本机 → localStorage 归零，但同步卡的 state 还是 246
回同步卡点「拉取」 → ?since=246 → 只拿到清空之后的变化
```

于是 7 条历史数据只回来 1 条，**界面还显示「拉到 1 条变化 · 新游标 …」，一切看起来正常**。
这就是他最初问的「本地清空了，云端数据能不能覆盖本地」——**在真实使用里，答案是「不能」**，
只是我第一次测的时候游标刚好是 0，侥幸通过。

### 改法：两处一起改，缺一不行

1. **请求起点不信 state**：`pullSince(loadCursor(currentUser), config)` —— 以 localStorage 为准。
2. **显示值跟着广播走**：`saveCursor()` 里 `window.dispatchEvent(CURSOR_CHANGED_EVENT)`，
   同步卡 `useEffect` 监听后重读。否则清空之后卡片上还显示旧游标，用户看到的是错数字。

只做第 1 条能修好功能但显示会骗人；只做第 2 条能修好显示但状态仍可能不同步。
