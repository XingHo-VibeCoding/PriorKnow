# 换用户编号：本机一本账 vs 云端分区（追加需求 `day24c`）

> 起因是他的一句复现：「换了用户编号再拉取，之前的用户数据还在。」
> 查下去发现这句话底下压着 **三个 bug**，其中两个他还没遇到、但后果更重。
> 本文只记「为什么这么改」，代码意图都写在对应文件的注释里。

---

## 一、三个 bug

| # | 现象 | 后果 | 谁发现的 |
| --- | --- | --- | --- |
| 1 | 换号后拉取，上一个号的任务还在列表里 | 两个账号混成一张表，**再也分不开**（本机没有 `user_id` 列） | 他 |
| 2 | 换号后点「推送本机任务」，会把任务整批写进新号名下 | **污染对方账号**。而且推完界面上还显示成功 | 我 |
| 3 | 游标全局只存一个（`priorknow-sync-cursor`） | 换号后拿 A 的 seq 去问 B，B 那边**序号更小的记录永远拉不到，且不报错** | 我 |

第 3 条最阴：它不会报错，界面还会显示「拉到 0 条变化 · 新游标 7」——
用户以为同步完成了，其实少了一半数据。

---

## 二、矛盾的根：本机一本账，云端按用户分区

- 云端：`tasks` 表有 `user_id`，每个接口都按它过滤（`WHERE user_id = ?`）。
- 本机：`tasks` 表**没有** `user_id` 列（IndexedDB schema 就 `'id, status, dueAt, importance, createdAt'`）。

这不是疏忽 —— 本机库从第 1 周就是「一个人的账本」，那时还没有账号这个概念。
所以「换号」在本机这件事上**没有中间状态**：要么这本账是 A 的，要么是 B 的，不可能同时是两个人的。

于是只有两条路：
- 给本机表加 `user_id`、所有查询带过滤（改动大，且 Dexie 要升版本迁移）；
- **或者**：认下「一本账」，换号就必须先把账清出去。

选了后者。理由：这本账的定位本来就是「当前用户的本机缓存」，不是多租户数据库。
真要支持两个账号来回切不丢数据，那是账号系统的事（登录上线后由认证决定身份，而不是文本框）。

## 三、改了什么

### 1. 游标按用户分开存

```ts
const CURSOR_PREFIX = 'priorknow-sync-cursor:'
loadCursor(userId) / saveCursor(userId, n)   // key = 前缀 + 用户编号
```

🔴 旧的那个不分用户的键**不做迁移**。换号后一律从 0 开始，代价是一次全量重拉；
全量重拉是幂等的（按 id 覆盖），比「猜一个游标」安全得多。

### 2. 记住「本机这批数据属于谁」

```ts
const OWNER_KEY = 'priorknow-owner'
loadOwner() / saveOwner(userId)
```

- 推送或拉取**成功后**才认领（失败的东西不该被认领）；
- `owner !== 当前编号` 就是那个必须先处理的状态。

### 3. 换号时拦住，并给一条出路

「云端同步」卡里出现一个虚线警示块，**标题点名两个号**：

> 本机数据属于「A」，不是「B」
> 这台设备只有一本账。现在点推送，会把「A」的 12 件任务写到「B」名下；现在点拉取，两个号的任务会混成一张列表 —— **之后再也分不开**。

下面是唯一的出路：`清空本机 12 件，切换到「B」`。三个按钮（推送 / 拉取 / 自检）同时禁用。

🔴 **不做成「点下去才报错」**：这里的错不是失败，是「会把数据写错地方」。失败可以重试，写错地方要收拾很久。
🔴 **不做自动清空**：清数据必须用户点头。确认框里写明「云端两边都不动，换回去再拉就能回来」——
    不说这一句，用户会以为按一下就全没了，于是宁可不点、继续混着用。

### 4. 「数据与设置」加清空入口

`清空本机 N 件任务`（带条数，库空时禁用）。换号那张卡是「被拦住时」的出口，
这个是「随时想清就清」的入口，两处都要有。

🔴 **清任务与游标归零必须一起做**。只清任务不归零，下次拉取从旧游标开始，
云端早期的记录永远拉不回来 —— 而界面上看起来一切正常。这是本次最难发现的一处。

### 5. 数据层补 `clearAll()`

```ts
clearAll(): Promise<number>   // 返回删了几条
```

不用 `importAll([])`：它也能清空，但语义是「导入一个空文件」，还会跑一遍规范化校验。
换用户这件事需要一个**说得出口**的方法名，调用处才读得懂自己在干什么。

## 四、验证时撞到的第三个坑：示例数据 id 撞号

改完后第一次线上跑「A 推 7 件示例」，7 件全被拒：

```json
{ "index": 0, "field": "id", "reason": "找不到这个任务（编号 sample-01）", "code": "NOT_FOUND" }
```

根因不是这次的改动，是**早就埋着的**：示例数据的 id 写死成 `sample-01`…`07`，
而 `id` 在云端是**全局主键**（不是「每个用户的第 01 号」）。
第一个把示例推上去的人就占住了这 7 个编号，第二个人推就撞「别人的行在本区不存在」→ 404 语义 → 整批被拒。

记忆里一直有一条「跨区测试前先 `DELETE … WHERE user_id='…'`」——
那是在**绕**它，不是在修它。而演示时正好会踩：载入示例 → 推上去 → 全红。

改法：`buildSampleTasks()` 给 7 条加同一个随机后缀（`sample-01-k3f9a2`）。
排序不受影响 —— 示例的 `createdAt` 已经互相错开一分钟，`compareEntries` 在第 3 步就分出先后，
永远走不到第 4 步的 id 兜底。

## 五、验证

### 本机（构建产物，`_owner-switch-check.mjs`）21 项全过

拦截出现 / 标题点名两个号 / 推送与拉取都禁用 / 游标显示跟着换成新号的 0 /
清空前弹确认且说明云端不动 / 归属改成新号 / 新号游标写 0 / **旧号游标原地保留** /
列表真的空了 / 空库时清空按钮禁用 / 设置页清空也真清空且游标归零 / 归属不变。

### 线上（两个真实测试账号，`_owner-public-e2e.mjs`）14 项全过

A 推 7 件 → 云端 7 条 → 换 B 被拦 → 清空切换 → 拉 B 得 1 条且**不含任何示例任务** →
换回 A 再被拦 → 清空 → 拉回 7 条 → **云端核对：B 名下仍只有 1 条，没有 `sample-*` 的 id**（证明没污染对方账号）。

测试账号 `e2e-a-1029` / `e2e-b-1029` 跑完已 `DELETE` 清掉；
库里剩下的 `demo-user-001`(9) / `xiaoquan`(5) / `None-user`(1) / `deploy-check-1029`(1) 是他的真实数据，一行没动。

### 过程中我自己写错的两条断言（不是 bug）

1. 拿 `.queue-title` 去读「全部任务」页 —— 那个类名只在首页存在，读到 0 条；
2. 断言弹窗只有 1 次 —— 载入示例自己也会弹确认，`dialogs[0]` 不是清空那次。

## 六、没做的

1. **本机表加 `user_id`**（真正支持两个号来回切）—— 那是账号系统的事，登录上线后再评估；
2. **自动同步**（打开即拉）—— 现在仍是手动点按钮，自动同步要先解决「谁是真身份」；
3. 回收站界面 —— 数据层已有墓碑，界面入口仍未做（老问题）。
