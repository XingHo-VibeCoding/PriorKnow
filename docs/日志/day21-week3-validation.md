### 关于第 1 项的一句实话

`db/schema.sql` 开头是 `DROP TABLE IF EXISTS tasks`，**故意做成破坏性重建** ——
Day 16 频繁调表结构时，「`CREATE TABLE IF NOT EXISTS` 静默跳过旧结构」比直接重建更危险。

代价是：**Day 17 起库里有真实数据，就不能在生产上重跑它了**（会删掉真任务）。
所以第 1 项的证据是在**进程内的真 PG（pglite）**里跑的，线上库一行没碰。
Day 17 之后的结构调整一律走增量迁移（`migrate-01-seq-trigger.sql` / `migrate-02-grant-write.sql`）。

## 演示提纲（3–5 分钟，四段结构）

> **这是什么东西**：不是代码、不是文档，是一份**口头讲解稿**。
> 想象对面坐着一个完全没用过这个产品的人，你要在 5 分钟内让他听懂「你这周做了什么、怎么做的、凭什么说做成了」。
> 顺序由课程第 1910 行固定为四段：**用户问题 → 核心流程 → 提示词改写 → 验证方式**。
> 每段下面第一句基本是可以直接念的开场句；凡是 ⬜ 的地方都要你自己填。

### ① 用户问题（约 40 秒）

任务清单类工具都在「记录」层内卷 —— 能记、能分类、能提醒，但**没有一个回答「我现在最该做哪件、为什么是这件」**。
知先回答的就是这一句：输入一堆散乱任务，算出一个分数，排出一个队列，并且把理由摊开给人看。

### ② 核心流程（约 2 分钟，必须含一次真实写入 + 刷新持久化）

1. 打开公网链接 → 点「确定访问」过中间页 → 首页「今日队列」
2. 加一条任务 → **它自己排进队列并给出理由**（不需要点任何「排序」按钮）
3. 进「全部任务」→「云端同步」→ 拉取 → **数据来自真实云端数据库**
4. **刷新页面 → 数据还在**（落进了本机 IndexedDB）
5. 点「专注」→ 只剩一件 + 倒计时 → 完成后下一件自动浮上来

### ③ 提示词改写（约 40 秒）

本周真实发生过一次，原始记录如下（可核对）：

- **第一版说法**：「云函数要连数据库」
- **实际发生**：AI 自己挑了 `pg` 直连，让我去环境变量里配数据库地址 / 用户名 / 密码；
  免费版根本不给这些 → 满控制台找、问 AI、查文档，**卡了 3 小时**
- **改写后**：「用 `app.rdb()` 把云函数接上数据库，**并告诉怎么查看接口输出**」
- **结果**：当天从 `pg` 切到 `app.rdb()`，第二天接口就上线

**三句判断（本人 10-29 原话，一字不改）**：

> 第一版只交代了任务，没有告诉AI小心踩坑，导致AI多轮坚持要我按错误的方法配置。该写 具体操作、行为兜底 是关键。如果已经知道文档、踩坑点、操作方式，把这些告诉AI，比如直接说通过 app.rdb() 实现云函数连接数据库；如果不知道，先分析云函数连接数据库的方式，遇到问题停下告诉我。

这段答到了两件 AI 侧的真实机制，值得单独记一笔：

1. **「只交代任务」= 把方案选择权默许给了 AI**，而 AI 会挑它最熟的那条（`pg` 直连），不是最省事的那条。
2. **「行为兜底」比「具体操作」更关键**：没有「遇到问题停下告诉我」这个停止条件，AI 会**在错误路径上自我强化**——越失败越坚持，因为它的目标函数是「完成任务」，不是「别在错路上耗着」。这也解释了为什么当时是「多轮坚持」而不是一次失败就转向。
