## 一、⚠️ 为什么推翻第一版（项目主人质疑后的判断）

**他的原话**：

> 我是希望上线用户云端同步功能的，也就是说服务器主要起到数据储存和同步的功能，
> 单靠前端就能实现云端以外的所有功能。为什么需要这么多获取数据的接口？

**第一版错在哪**：我按「前端是一个普通 CRUD 客户端」写了 7 个接口
（读全部 / 读单条 / 新建 / 改 / 删 / 整体覆盖）。这套写法的前提是
「**后端是数据的主人**」—— 每次只动一条、每条单独校验、怕别人改坏你的数据。

**但本项目的架构前提相反**：**后端只是仓库**。算分、排序、筛选、「为什么排这里」
全在前端（`TECH_DESIGN.md` 第一节原话：「算法放前端更快」）。
仓库不需要知道你在对哪一条做什么，它只需要「存下来、给出去」。

而且证据本来就在仓库里 —— `app/src/data/repository.ts` 第 45–48 行那对
`exportAll()` / `importAll(tasks)`，本身就是「**整份进、整份出**」的语义。
**第一版绕过它去设计单条增删改，是把简单的事复杂化了。**

### 🔴 更要紧的：第一版连「同步」这个目标都没解决

第一版只有「CRUD 操作」，没有「把两台设备对齐」这件事的接口 ——
每次同步都要拉整份（8 KB），而**省下的只是提交那一半**。

真正省流量的做法是**增量同步**（本版采用）：给每条记录一个自增序号，
客户端记住「我上次同步到第几号」，下次只要问「比这号新的有哪些」。
**这样拉取和提交双向都是几百字节**，而且**不需要「算 diff」那种复杂逻辑** ——
每条带自己的序号，前端只要比一下大小。

⚠️ **但要说清一点：合并这一步在前端，不在云端。**
云端只负责发号，「谁的号大谁赢」的比对是前端做的 ——
不写这段代码，云端返回的旧记录会覆盖用户刚在本地改的内容。
准确的规则名是「**最后写入者赢**」（取舍 6），不是「本地优先」。

### 改了什么（第一版 → 本版）

| | 第一版 | 本版 |
| --- | --- | --- |
| 业务接口数 | **7 个** | **2 个** |
| 表字段 | 7 个 + `user_id` | 7 个 + `user_id` + **`seq`** + **`deleted_at`** + **`purged_at`** |
| 拉取方式 | 每次整份（8 KB） | `?since=N`，**没变化就几十字节** |
| 提交方式 | 逐条（4 个不同接口） | 一个 `POST`，body 收数组，**可打包多条** |
| 合并逻辑放哪 | **前端**（要算 diff） | **前端**（比 `seq` 大小，云端只负责发号） |
| 回收站 | 无 | **有**（`deleted_at` 回收站 + `purged_at` 墓碑） |
| 全量覆盖接口 | 有（`PUT`） | **删掉** —— 与增量同步冲突，理由见第六节末尾 |
| `OPTIONS` / CORS 预检 | 没提 | **规定放行 204**，不做 Day 20 全挂 |
| 墓碑清理 | 没写 | **90 天，惰性清理**（第五节） |
| 同步时机 | 没写 | **登录后默认开、未登录不同步**（取舍 8） |
| 账号体系 | 「不做登录」 | **改为「Day 22 之后做」** —— 课程列它是选做，不阻塞部署（取舍 9） |

⚠️ **第一版还有三处洞，第二版才补上**（都是评审挑出来的，
写在这里是因为它们印证了「契约必须能被实现」这件事）：

| 第一版的洞 | 后果 |
| --- | --- |
| 没写 `seq` 不可被请求体覆盖 | 一句 `SET seq = 请求体.seq` 就能让序号回退，**整套同步自我摧毁** |
| `POST` 的 `cursor` 没写「本区」 | 实现成 `SELECT max(seq) FROM tasks` 就**永久丢数据** |
| 「游标失效云端认得出」 | 云端没有「有效游标」状态，**这条根本无法实现** |

## 二、已拍板的取舍（Day 15 板块④）

### 1. 优先级分数与理由**在前端算** → 接口不返回 priority 字段

- **理由**：权重一定会调。放后端意味着改一句理由文案要改 SQL **并重新部署云函数**；
  「可解释排序」是本项目唯一的差异化卖点（`research.md` 结论），不能让它卡在部署上。
- **代价**：每次拉回来的数据要自己算分。**但增量同步下这个代价变小** ——
  没变化时一条都不用算，只算新来的那几条。
- **对齐处**：`TECH_DESIGN.md` 第五节已写明「派生值不入库」，本契约是它的接口层落地。

### 2. 数据按 `user_id` 分区，`user_id` = **浏览器本地随机 ID**

⚠️ **时效：本条说的是「现在」。Day 22 之后会改为 CloudBase 内置认证的登录态 uid**
（取舍 9）。届时本条下面那句「⚠️ 它不是登录」和「清缓存即换区」都随之失效 ——
**但 `user_id` 这一列的类型、第四节那两道校验、第六节接口的形状都不变。**

- 客户端首次打开页面时生成一个随机 ID 存进 `localStorage`，之后每个请求带上。
- 服务端**不校验、不问「你是谁」**，只拿这个字符串分组。
- **效果**：自己的浏览器看到自己的数据；换浏览器或清缓存就是一个新 ID
  （旧数据还在库里，但找不到了 —— 这是「不做登录」的必然结果）。
- ⚠️ **它不是登录**：拿到这个 ID 就能看那一区的数据，清缓存就丢。
- **为什么现在做**：课程第 1074 行「不要新增登录和支付」，所以不做登录；
  但第 1150–1163 行说「数据不丢」由 Day 15–21 白送。**分区是「不丢」的前提** ——
  不分区的话所有浏览器共用一区，任何人打开公网链接都能看到并改你的任务。

### 3. 「载入示例数据」→ **`db/seed.sql` 手工执行**，不写接口

- 依据课程第 1358 行：seed 脚本必须可重复执行 —— 这天然是 SQL 脚本的活。
- 前端那个按钮在云端版改成提示「请在控制台执行 `db/seed.sql`」。
- **为什么这么选**：那个按钮的行为是「清掉全部数据再塞 7 条假数据」。
  放在公网上任何人可调，等于给作品开了个「一键清库」的后门。

### 4. 增量同步，**双向几百字节**

- 云端每条记录编一个自增序号 `seq`，客户端记住上次同步到的值（游标）。
- **代价**：表多两个字段；首次同步或游标失效时仍要拉一次全量
  （所以第 1 条接口要同时支持「带 `since` = 增量」和「不带 = 全量」两种模式）。

### 5. 删除走**回收站**，可在特定界面真删

- 删除 = 给 `deleted_at` 填一个时间戳，**记录还在**（所以能跟着同步）。
- 在回收站界面里可以「彻底删除」，那条才真的从库里消失。
- ⚠️ **回收站的记录也要编 `seq`**，否则「A 电脑删了、B 电脑看不到」。

### 6. 冲突**最后写入者赢**（⚠️ 原先叫「本地优先覆盖」，那个名字是错的，已改）

- 同一区里同一条任务，两台设备都改了 → **谁的 `seq` 大谁赢**。
- **准确含义**：云端按**到达顺序**发号，所以这等于「谁最后推到云端谁赢」。
  它**不是**「本地优先」—— 云端看不出「谁更该赢」。

**⚠️ 这里曾经写错，且名字错了会让人写错代码**：
原稿写「本地优先覆盖」，听起来像是「本地刚做的改动不会被云端陈旧数据盖掉」——
**但 `seq` 给不了这个保证**：

```
A 把 X 标成 done → 云端 seq=101
B 离线很久，本地 X 还是 todo，因为改标题而推送 → 云端 seq=102
A 拉取，拿到 102 → 如果 B 推的是完整记录，A 的 done 就被 B 的陈旧状态覆盖了
```

**为什么实际很少发生**：契约规定「**只更新请求体里出现过的字段**」，
所以 B 推 `{id, title}` 不会覆盖 `status`。**但这不是保证，是概率。**

**要真正的冲突检测必须加 `baseSeq`（乐观锁）**：推送时带上「我改这条时它云端是第几号」，
云端发现号变了就拒。本版**不做** —— 代价是离线设备重推容易被拒，
得配一套「先拉后推」的流程，复杂度上一个台阶。
（⚠️ 原稿写「取舍记在第十一节」但那张表里没这一行 —— 已补到第十一节。）

### 7. 前端合并规则（Day 17 必写，这条不能省）

**拉回来的记录与本地同 `id` 冲突时，`seq` 大的赢，`seq` 小的丢弃。**

⚠️ **这条必须由前端实现 —— 不能理解成「云端已经比过了所以前端不用管」。**
云端只负责发号，**比大小这一步在前端**：不写合并规则，
云端返回的**旧记录会覆盖用户刚在本地改的内容**（本地那条 `seq` 更大，但没人比）。

合并的完整算法（Day 17 按这个写）：

```
对 items 里每一条远端记录 r：
    if r.purgedAt 非 null  → 从本地库真删这一条（先做，不比 seq）
    本地同 id 的记录 l = 本地按 id 查到的那条
    l 不存在        → 直接插入
    比较 seq（两边都先归一化，见下）
    r.seq > l.seq   → 用 r 整体覆盖 l（含 seq）
    r.seq <= l.seq  → 丢弃 r（本地更新，保留）
```

🔴 **`seq` 归一化：本地新建的任务 `seq` 初值必须是 `0`**

这是第一版漏掉的，**不写清 Day 17 照着写就会踩**：

| 情况 | 本地那条的 `seq` | 比较前要归一化成 |
| --- | --- | --- |
| 本地新建、**还没推过云端** | `0`（**契约规定，不是 `null`、不是 `undefined`**） | `0` |
| 云端已有 | 云端返回的真实 `seq` | 原值 |

⚠️ **为什么必须写死初值**：如果不规定，`r.seq > l.seq` 里的 `l.seq` 是 `undefined`，
`187 > undefined` 求值为 **`false`** → 走「丢弃 r」分支 →
**远端那条被丢掉，本地那条永远没有 `seq`**，也就永远推不上云端、
永远拿不到兜底修正后的值。这是个静默失败，不报错。

⚠️ **所以 `Task.seq` 的类型是 `number`（不是 `number | null`），新建时给 `0`。**
⚠️ **收到墓碑（`purgedAt` 非 null）时直接真删本地那条，不走 seq 比较** ——
墓碑没有「谁更新」的问题，它的意思是「这条已经不在了」。

### 8. 同步时机：**登录后默认自动同步，可改为手动；未登录不同步**

**已拍板（原话：「自动同步在用户注册时询问是否开启，默认开启
（登录开启云同步，可改为手动），未登录时不同步」）**

🔴 **先说清时间轴，否则 Day 17/18 会照着写死**

「未登录」这个状态**只在登录功能落地之后才存在**（取舍 9：Day 22 之后）。
Day 17–22 期间**没有登录态可判**，所以下面表格的第一行在那段时间不适用：

| 时期 | 判定 | 行为 |
| --- | --- | --- |
| **Day 17–22（登录未落地）** | 一律按「已登录 + 开关开」 | **直接自动同步，不弹询问**（还没有「同意」这个概念） |
| **Day 23 起（登录已落地）** | 未登录 | 🔴 完全不发同步请求 —— 不拉也不推 |
| Day 23 起 | 已登录 + 开关**开**（默认） | 打开页面自动拉一次；本地改动后自动推 |
| Day 23 起 | 已登录 + 开关**关** | 全部手动 —— 页面上「立即同步」按钮 |
| Day 23 起 | 已登录 + **尚未选择**（弹窗中） | 不发任何请求；选完才按上面两行执行 |

⚠️ **如果不写清这条，第一版读法会让同步在 Day 17–22 一次都不触发** ——
那时所有用户都是「未登录」，而未登录不发请求。
**这会让 Day 17/18 的两个接口完全无法验收。**

**「默认开启」怎么落地 —— 不是一上来就自动同步，而是先问一次**：

```
Day 23 起，登录成功那一刻
  → 弹一个询问：「是否开启云同步？开启后你的任务会在多台设备间保持一致」
     [ 开启 ]（默认选中的按钮）   [ 暂不 ]
  → 选「开启」→ 记下这个选择，此后自动同步
  → 选「暂不」→ 不发任何请求；页面上仍有一个「开启云同步」入口，随时能改
```

⚠️ **两个入口按钮不要混**（文案相近，实现时容易做成同一个）：
**「开启云同步」= 改开关（改完就一直自动）**；
**「立即同步」= 手动推拉一次（不改开关）**。

⚠️ **「默认开启」指的是默认选中的按钮是「开启」，不是不问就自动开始上传。**
理由：不问就上传 = 用户还没同意，数据已经离开本机了。
而默认选中「开启」= 想同步的人一步就能开始，不想的人明确点过「暂不」。

**这个询问只弹一次**，选择结果要记住（存哪见第十一节）。以后随时能在设置里改。

🔴 **「未登录不同步」是产品底线（由前端保证，服务端无法强制），不是性能优化**：

| | 说明 |
| --- | --- |
| **为什么** | 数据传到了别人能访问的服务器上。不打招呼就传，用户没同意 |
| **谁保证** | ⚠️ **只能由前端保证** —— 服务端没有任何机制能强制（`X-User-Id` 可伪造，见第七节不一致 2）。**别以为服务端在校验这件事** |
| **未登录的代价** | 数据**只在本机**。不同步本身不带来额外丢失 —— 但**这不等于未登录也有备份**： |

⚠️ **「未登录也没有副本」这件事必须写清，别让「不丢」被读成「安全」**：

- `user_id` 存在 `localStorage`、任务数据存在 `IndexedDB`，
  **两者在同一个浏览器存储里 —— 清缓存或换浏览器会一起消失**（取舍 2 已写明）。
  未登录时云端**没有**任何一份副本。
- 而且**彻底删除目前还没有回收站兜底**（第十节 C 组第 9 条才要改成软删），
  在那之前误删即真删，本地云端都没有。
- 想要一份带得走的备份，用「导出 JSON」。

**与登录排期的关系**：本条依赖账号体系，而账号体系排在 **Day 22 之后**（见取舍 9）。
在那之前 `user_id` 是浏览器随机 ID，**同步功能照常可用**，
「登录」只是把「同一台设备」变成「同一个账号的所有设备」。

### 9. 账号体系：**Day 22 之后再做**，用 CloudBase 内置认证

**已拍板。** 课程第 2880–2887 行把登录列为「选做，不得阻塞部署」，
并明确警告「不要在最后几天临时加入登录，导致核心闭环无法验收」。
所以它排在核心闭环（同步）验收完之后。

| 决定 | 结论 |
| --- | --- |
| 时机 | **Day 22 之后**，不阻塞同步的验收 |
| 方式 | **CloudBase 内置认证**（邮箱密码 / 手机验证码 / 微信），不自写哈希与会话 |
| 旧匿名数据 | **不迁移** —— 登录后从空库开始 |
| 关闭同步后 | **云端数据保留**，只停自动推拉，不换 ID |

⚠️ **换 ID 只由「登录」触发，与同步开关无关** ——
关掉同步期间 `user_id` 不变（已登录的话就是登录 uid）。
这两条讲的是不同的事，别读混。

**为什么不自写邮箱+密码**：课程第 2886 行要求登录必须处理
「密码哈希、会话、权限、退出、隐私、线上环境变量」六件事，
内置认证做掉前两件（**权限那件仍要我们自己做** —— `tasks` 按 `user_id` 过滤），
剩下三件加起来约 1–2 天；自写则要 4–6 天，且哈希算法选错就是安全漏洞。

**为什么不迁移旧匿名数据**：

⚠️ **理由要说准 —— 不要说「现在云端没有数据所以无感」，那是错的**：
Day 17–22 同步功能是**可用的**（取舍 8 第一行），所以到 Day 23 换 ID 那天，
**云端很可能已经有匿名区的数据了**。

不迁的后果就是第四节写的那条：**那些数据变成用户再也看不到的孤儿行**。
**认这个后果** —— 那时用户已经有「导出 JSON」的习惯，
而且课程把登录明确列为「选做，不得阻塞部署」，
为它写一套迁移（一次 `UPDATE` + 一个接口参数 + 旧 ID 的存取与清理）
不属于核心闭环。**但不要因此认为换 ID 是无感的。**

🔴 **`user_id` 这一列一个字都不用改** —— CloudBase 内置认证的用户 ID 形如

登录做完后，把登录态的 uid 填进**同一个** `user_id` 列 ——

**这是当初把 `user_id` 设计成「随机字符串」而不是「自增整数」换来的好处。**

⚠️ **内置认证的两个已知成本（Day 22+ 那天要处理，不是现在的拦路虎）**：
① 登录页在平台域名 `env-xxx.tcloudbaseapp.com` 下，
**要在控制台配 HTTP 访问域名白名单**，否则 Web 端被拦；
② 账号数据存在 CloudBase 的用户体系里，不在我们自己的 `tasks` 表里。

## 三、响应形状（统一壳）

课程第 1456 行原话：「成功时 `ok` 为 true、数据放在 `data` 里；
出错时 `ok` 为 false、`error` 里放人能看懂的中文说明。前端以后只认这一个形状，所有接口都不例外。」

```jsonc
// 成功 —— 两个字段都恒存在
{ "ok": true, "data": <任意形状>, "error": null }

// 失败
{ "ok": false, "data": null, "error": "任务标题不能为空" }
```

**约定：`data` 与 `error` 恒存在，只有一个为 `null`。**
理由：前端写 `res.data.items` 不用先判 `error` 是不是 undefined，少一类分支。

⚠️ **唯一的例外：`POST` 的 400 响应额外携带顶层 `rejected` 数组**。

因为「一条都没收下」时也要告诉用户**每条为什么被拒**，而 `data` 按约定必须是 `null`：

```jsonc
{
  "ok": false,
  "data": null,
  "error": "这批数据一条都没收下，你原来的数据没有被改动",
  "rejected": [ { "index": 0, "reason": "任务标题不能为空" } ]   // ← 顶层，不在 data 里
}
```

⚠️ **只有这一种情况允许额外字段**，其他响应一律严格三个字段。

### HTTP 状态码

| 码 | 什么时候用 | `error` 的内容 |
| --- | --- | --- |
| 200 | 成功（`GET`） | `null` |
| 201 | 推送完成（`POST`，至少有一条被接收） | `null` |
| 400 | 参数缺失 / 格式错 / 校验不过 | 具体中文说明，**要说清缺了什么** |
| 404 | **路由不存在** | `没有这个接口（路径 xxx）` |
| 404 | **任务不存在，或不属于本区** | `找不到这个任务（编号 xxx）` |
| 405 | 方法不对 | `这个接口不支持 {方法}，只支持 {允许的方法}` |
| 409 | 重复提交（见第六节第 2 条的「重复提交（防重）」小节） | `已有一条内容相同的待办：xxx` |
| 500 | 服务端内部错误 | `服务器内部错误，请稍后再试`（**不把堆栈暴露给前端**） |

⚠️ **404 与 403 合并**：不属于你的任务**也**返回 404，不返回 403。
理由：返回 403 等于确认「这个 id 存在」，泄露别人的数据有无。

⚠️ **405 的文案里方法名要跟着变**：`POST /api/tasks` 被 GET 调用时，
要说「不支持 GET，只支持 POST」，不能一律写「只支持 GET」。

🔴 **`OPTIONS` 必须放行 —— 不做这条，Day 20 从 localhost 切公网时所有请求全挂**

因为 `X-User-Id` 是**自定义请求头**，所有 `/api/tasks` 请求都算「非简单请求」，
浏览器会**先发一个 `OPTIONS` 预检**。契约规定：

| 请求 | 响应 |
| --- | --- |
| `OPTIONS /api/tasks`（或任意路径） | **204**，可带空 body |
| 响应头至少含 | `Access-Control-Allow-Origin: <前端域名>`（**不要用 `*`**，课程第 1208 行明说）<br>`Access-Control-Allow-Headers: Content-Type, X-User-Id`<br>`Access-Control-Allow-Methods: GET, POST, OPTIONS` |

⚠️ **`OPTIONS` 不算 405。** 405 只给「路径对、方法确实不在允许列表里」的真实调用。

🔴 **为什么这条特别容易漏**：现有 health 实现写的是
`if (method !== 'GET') return 405`（`cloudfunctions/api-health/index.js:96`）——
**照抄这个写法，`OPTIONS` 会被自己拒掉，预检失败，`GET` 根本发不出去。**
而报错是浏览器控制台的 CORS 错误，**不是接口错误**，排查时极难定位。

（具体跨域配置在 Day 20 的控制台里做，契约只要求云函数这一侧放行 OPTIONS。）

⚠️ **404 有两种语义，代码要分开**：路由不存在（网关没匹配到任何函数路径）
和任务不存在（函数内部查库没查到）是两回事，`error` 文案不同。

## 四、`user_id` 怎么传（⚠️ 这是我定的，请确认）

**用请求头 `X-User-Id`。**

```http
GET /api/tasks?since=186 HTTP/1.1
Host: priorknow-d0go4uh2uc0f62465.service.tcloudbase.com
X-User-Id: 3f9a1c2e-....
```

**为什么不用查询参数 `?userId=`**：
① URL 会进服务器日志、也会出现在截图和 F12 的 Network 面板里；
② 语义上它是「身份」不是「筛选条件」，放查询参数容易被误当成可篡改的入参。

**代价（必须提前知道）**：自定义请求头属于「非简单请求」，
**Day 20 配 CORS 时要把 `X-User-Id` 加进 `Access-Control-Allow-Headers`**，
否则跨域会被浏览器拦掉 —— 报错关键词是 `Access-Control-Allow-Headers`，
与 Day 20 文档里写的 `Access-Control-Allow-Origin` **不是同一个**，
别照着只配 Origin。

**缺失或格式不对时怎么办**（两道校验，都要写进代码）：

| 检查 | `error` | 为什么 |
| --- | --- | --- |
| 头不存在，**或去掉首尾空格后为空** | `缺少 X-User-Id 请求头` | 空字符串等于没带 —— 不然所有空头请求会混进同一区 |
| 长度 > 64，或含 `[A-Za-z0-9_-]` 以外的字符 | `X-User-Id 格式不对` | 这个字符串会直接变成库里的分区键，不校验就等于允许任意内容进库 |

**不自动生成、不填默认值。** 静默兜底是这里最大的坑：
不校验就意味着所有漏带头或带头为空的用户请求全落进同一个分区，
表面上"能用"，实际上数据已经串了。

### 🔴 `user_id` 的取值会变一次，但**格式不变**（Day 23 之后）

| 时期 | `X-User-Id` 传什么 | 后果 |
| --- | --- | --- |
| **现在 → Day 22** | 浏览器 localStorage 里的**随机 ID** | 换浏览器 / 清缓存 = 换区，旧数据找不回来 |
| **Day 23 之后（已定）** | CloudBase 内置认证的**登录态 uid**（形如 `user_8f2a`） | 同一账号多台设备共享一批数据 |

🔴 **正因为当初把它设计成「随机字符串」而不是自增整数，这两种取值才能共用一列** ——
CloudBase 内置认证的 uid 形如 `user_8f2a`（前缀 + 十六进制），
符合第四节的格式规则（1–64 且只含 `[A-Za-z0-9_-]`），
**所以 `db/schema.sql` 的 `user_id` 列、第四节那两道校验、
第六节两个业务接口的形状，一个字都不用改。**
换的只是「前端往这个请求头里填什么」。

⚠️ **上面这条断言有一个前提，Day 20 实现时必须守住**：
**匿名 ID 一定要生成在第四节允许的字符集里** ——
用 `crypto.randomUUID()`（含 `-`，在允许集内）或 `Math.random().toString(36)`。
**不守住的后果**：哪天随机 ID 里带上一个 `.`，
Day 23 换 uid 之后所有请求会被自己的格式校验全拒（400），而原因极难定位。
**契约只规定「校验规则」，没规定「生成规则」—— 这一条现在补上。**

⚠️ **Day 23 落地时用真实 uid 实测一次再定稿**：自定义登录允许自定义最长 64 位的 uid，
官方文档没有写明字符集。本项目不用自定义登录（用默认邮箱/验证码），
但**断言要在真机上验过才能当事实**。

⚠️ **但要有心理准备**：换 ID 那一刻，**匿名期同步上去的数据会「消失」**
（它们在旧区，新 ID 是新区），变成用户再也看不到的孤儿行。
取舍 9 已定**不迁移** —— 认这个后果，但别以为换 ID 是无感的
（Day 17–22 同步可用，那时云端很可能已经有数据了）。

⚠️ **即使有了登录，`X-User-Id` 仍然不是身份凭证** ——
服务端读法还是「请求头写什么就取什么」，任何人能伪造它去读别人的区。
**真正的校验在登录系统那一层**（前端拿到的登录态才是真的）。
这个请求头永远只是**分区键**，详见第七节不一致 2。

### ⚠️ 截图与公开链接里不要出现真实 `X-User-Id`

它是分区键，出现在 Day 20 的验收截图或公开链接里就等于把那一区的数据交出去。
课程第 245 行的「可公开」清单里只有环境 ID 和域名，不含它。

## 五、表结构（Day 16 建 `db/schema.sql` 的依据）

**一张表 `tasks`。** 字段全部来自 `TECH_DESIGN.md` 第五节，
在此基础上按增量同步与回收站两条决策加 `seq` / `deleted_at` / `purged_at`。
⚠️ **三个都要建** —— 第一节与第九节写的也是三个，只有这里曾漏了 `purged_at`。

| 列名 | 类型 | 可空 | 默认 | 说明 | 前端字段（camelCase） |
| --- | --- | --- | --- | --- | --- |
| `id` | `text` | 否 | — | 主键，**前端生成**（见下方说明） | `id` |
| `user_id` | `text` | 否 | — | 分区键，见第四节 | （不进响应体） |
| `seq` | `bigint` | 否 | — | **变更序号**，云端自增。**任何一条一变就往前挪** | `seq` |
| `title` | `text` | 否 | — | 任务内容，去首尾空格后 1–200 字 | `title` |
| `due_at` | `timestamptz` | **是** | `NULL` | 截止时间；**没有期限就是 NULL，不能存 0 或空串** | `dueAt` |
| `estimate_minutes` | `integer` | **是** | `NULL` | 预计耗时（分钟）；**未估算必须是 NULL，不能存 0** | `estimateMinutes` |
| `importance` | `smallint` | 否 | `3` | 重要度 1–5 | `importance` |
| `status` | `text` | 否 | `'todo'` | `todo` / `doing` / `done` | `status` |
| `created_at` | `timestamptz` | 否 | — | 创建时间（**前端给**，见下方说明） | `createdAt` |
| `deleted_at` | `timestamptz` | **是** | `NULL` | **回收站**：填了时间戳 = 已删除、可恢复；`NULL` = 正常 | `deletedAt` |
| `purged_at` | `timestamptz` | **是** | `NULL` | **墓碑**：填了时间戳 = 已在回收站被彻底删除。⚠️ **行还在**，见下方说明 | `purgedAt` |

### 🔴 彻底删除必须留「墓碑」，不能真删行

**问题**：如果 `purge` 直接 `DELETE` 掉那一行，
「X 已被彻底删除」这个事实就**没有任何载体携带**：

```
A 设备 purge 了 id=X（seq=100 被消耗）
B 设备 since=50 → 云端 seq>50 的记录里，没有任何一条提到 X
→ B 永远保留 X，而且每次同步都收不到任何变化
```

**序号还在但没有任何行携带它，对增量拉取毫无意义。**
（第一版想用「`seq` 只增不减」解决这个问题，那是错的 ——
 号在**没有行**里，等于不存在。）

**所以契约规定**：`purge` 时**保留行**，只把 `purged_at` 填上时间戳，`seq` 照常前进。
`GET` 照常返回这条墓碑（带 `purgedAt`），前端见到就把本地那条**真删**。

**「真删」的准确含义是「从两个界面都看不到」，不是「从数据库物理移除」。**

🔴 **墓碑保留 90 天，期满物理删除**（已拍板）

| 项 | 规定 |
| --- | --- |
| 保留期 | **90 天**，从 `purged_at` 的时间戳算起。⚠️ **期满后「最迟在该区下一次 `POST` 时」删除**，不是定时器 —— 见下方警告 |
| 判定 | `purged_at IS NOT NULL AND purged_at < now() - interval '90 days'` |
| 谁来清 | 云端**惰性清理** —— 不需要定时任务，见下 |
| 删的行 | 只删墓碑行（`purged_at IS NOT NULL` 且已过期）。**正常的 `deleted_at` 行（还在回收站）永不自动删** |

**为什么不设定时任务**：定时触发器要额外配置、要额外计费、
而且**没人往库里写数据时它也只在空跑**。惰性清理的逻辑是：

```
每次 POST /api/tasks（推送）成功之后，顺手跑一次：
    DELETE FROM tasks
     WHERE purged_at IS NOT NULL
       AND purged_at < now() - interval '90 days'
       AND user_id = 本区
```

⚠️ **只在推送时清，不在拉取时清** —— 拉取是用户高频操作，
每次拉都跑一次 DELETE 是白花钱。而推送天然会触发（用户有改动才会推）。

🔴 **「90 天」不是定时器，是「下推时顺手清」—— 不要说成「90 天后一定删」**

一个区若长期没有任何推送，它的过期墓碑会**一直留着**。
**体积可忽略**（一条约 200 字节，一年也就几十 KB），但契约不许承诺做不到的事。
要真正定时清理就得配定时触发器 —— 那是 Day 23+ 的事，本期不做。

🔴 **90 天这个数字够不够 —— 必须认这个后果**：

超过 90 天才连上云的设备，**收不到那个墓碑**，
它本地那条被彻底删除的任务会**一直留着**。后果分两种：

| 情况 | 后果 |
| --- | --- |
| 那条任务在设备 A 上已被 purge，设备 B 离线 100 天后回来 | B 上会看到这条任务，**点开发现云端已没有它**；B 再改动它时会被拒（`rejected`：`这个任务已被彻底删除，不能恢复`） |
| 用户不理解 | 看到一条「幽灵任务」，删掉后再次创建同一内容 → 因为 409 判重排除了墓碑，**能建成功** |

**为什么 90 天够用**：一台设备离线超过 3 天的概率极低，
而墓碑的体积很小（一条约 200 字节，一年也就几十 KB）。
**如果以后要支持「长期离线设备」，把 90 天改长即可 —— 只改这一处常量。**

⚠️ **不要为了「让幽灵任务消失」而把墓碑立刻删掉** ——
那样删除操作就传不到别的设备，重新变成第一版的洞。

🔴 **清理会让本区 `max(seq)` 变小 —— 第六节的 `notice` 文案要能容忍这一种**

墓碑清理 `DELETE` 掉的是**本区**的行。若某区的行全是过期墓碑、被清空，
本区 `max(seq)` 就没了。老设备带 `since=100` 回来 →
按第六节规则「`since` 比本区最大 seq 还大 → 当作全量 + `notice`」。

⚠️ **但这种情况不是「云端被重建过」** —— `notice` 里那句
「本地游标比云端还新，已重新拉取全量」会让实现者以为云端出故障了。

**契约规定**：`notice` 的文案要写成**中性的事实陈述**
（如「已重新拉取全量数据」），**不要带上「本地游标比云端还新」这种推断** ——
推断在墓碑清理存在之前是对的，现在有两种原因会造成同样的现象。

⚠️ **返回全量本身是安全的**：库里确实没东西了，全量就是正确的响应。

⚠️ **墓碑带来的三个后果，都要认**：
1. 库里会积墓碑记录 —— **但已定 90 天自动清理**，见上；
   单区上限约「90 天内、且该区有推送的删除次数」。⚠️ 长期不推送的区会略多于 90 天 —— 见上方警告
2. **墓碑记录要不要返回给前端**：本契约规定**要返回**（带 `purgedAt`），
   否则本地那条删不掉。⚠️ 前端见到要**真删本地记录**，别只是标记
3. **判重时要排除墓碑**：`purged_at IS NULL` 才参与判重，
   否则「彻底删掉一条又新建同样内容的」会被 409 拒

### 🔴 `id` 列用 `text`，不用 `uuid`

**理由**：本地实现的 `newId()`（`local-indexeddb.ts:139–144`）在**非安全上下文**下
会退回 `t-${时间戳36进制}-${随机串}`，形如 `t-mfk3x2-8a1b2c3d` —— **不是 UUID**。
公网页面走 https 是安全上下文，但本地开发可能不是，
而且历史上已经存进本地库的那些 id 就是这个形状。

所以 `id` 的校验规则是**宽松格式**：

| 规则 | 值 |
| --- | --- |
| 长度 | 1–64 |
| 允许的字符 | `[A-Za-z0-9_-]` |
| **合法示例** | `9c1f2a7e-4b3d-4a1f-8e55-2d0c9b7a1e34`（UUID）、`t-mfk3x2-8a1b2c3d`（本地历史 id） |

⚠️ **这条要是写成「必须 UUID」，Day 17 照着实现就会断掉一条真实路径**：
本地导出的数据里全是 `t-` 开头的 id，推到云端后会被 400 拒掉。

### 🔴 `id` / `createdAt` 由**前端**生成（与第一版相反，理由见下）

| 字段 | 谁生成 | 为什么 |
| --- | --- | --- |
| `id` | **前端** | 增量同步下前端要能**离线新建并立刻看到它**，不需要等网络往返。**已有实现不用改** —— `local-indexeddb.ts:58` 现在就是前端生成 |
| `createdAt` | **前端** | 理由同上。而且它是「全部任务」页倒序的依据，浏览器时间在这里够用 |

⚠️ **第一版写的是「服务端生成」，本版改掉了。** 当时的理由是
「防止客户端伪造主键 + 前端时钟不可信」—— 但**增量同步下服务端不再是数据的主人**，
那条理由不成立了。而且如果 `id` 要服务端生成，
**「先在本地加一条、立刻看到它」这个体验就做不到**（要等一次网络往返），
那与「本地优先」的架构相反。

⚠️ **那 `seq` 为什么还是云端给？** 因为它是**顺序的权威依据** ——
两台设备各自新建的任务，`id` 谁大谁小没有意义，
只有云端统一编号才能定义「谁更新」。**`id` 是身份（前端给），`seq` 是顺序（云端给），两件事分开。**

⚠️ **那 `createdAt` 用浏览器时钟，会不会像时间戳增量那样出问题？**
不会 —— 它只影响「全部任务」页的展示顺序，
**不参与任何算分**（`core/priority.ts` 只用 `dueAt` / `importance` / `estimateMinutes`），
也不参与增量判断（那是 `seq` 的事）。所以时钟不准只会让排列顺序有点怪，
不会导致同步出错。

### 🔴 `seq` 怎么生成 —— 不要自己数

**用 PostgreSQL 的自增序列，并且必须写成 `generated always as identity`**：

```sql
-- ✅ Day 16 就这么写
seq bigint generated always as identity
```

⚠️ **为什么必须是 `always` 而不是 `by default`**：

| 写法 | 客户端传了 `seq` 会怎样 |
| --- | --- |
| `bigint default nextval(...)`（= `by default`） | **静默接受** —— 显式给的值覆盖默认值，`seq` 可被回退 |
| `bigint generated always as identity` | **直接报错** —— 除非写 `OVERRIDING SYSTEM VALUE`，天然堵死这条路径 |

**两种写法 Day 16 选哪个，Day 18 的行为完全不同**，所以这里定死用 `always`。
它相当于在数据库层加了一道保险 —— 即使代码写错了、即使前端把 `seq` 传上来，
数据库也不会让序号退回去。

（这不是说可以不管白名单校验，而是**两层保险比一层好**：代码层写对了是常态，
数据库层挡住「万一写错了」的情况。）

⚠️ **绝对不要用 `SELECT max(seq) + 1` 自己算** ——
两个请求同时来时会拿到同一个值，出现两条记录 `seq` 相同，
而「比 `seq` 大的才算新」这个判断就失效了，**同步会静默漏掉一条**。

⚠️ **`seq` 只增不减**：哪怕记录被移入回收站、被彻底删除，序号也不回收。
所以「上次同步到 186」这个游标**永远有效**，不会因为中间少了号而出问题。

### 索引

⚠️ **索引只为「契约里真实存在的查询」而建**，不为「将来也许会用」而建。

| 索引 | 定义 | 契约里谁在用它 |
| --- | --- | --- |
| 主键 | `PRIMARY KEY (id)` | 推送时按 id 判断新增还是改；拉回来后按 id 合并进本地 |
| 增量扫描 | `(user_id, seq)` | **第 1 条的核心**：`WHERE user_id = ? AND seq > ? ORDER BY seq` |

⚠️ **第二条索引是增量同步的性能命脉** —— 没有它，每次拉取都要全表扫再过滤。

### ❌ 不建的字段

| 不建 | 为什么 |
| --- | --- |
| `priority` / `score` | **派生值不入库**。权重一调，存下来的分数全过期（取舍 1） |
| `dependency_ids` | PRD 第四节已把「复杂依赖关系」列为本期不做 |
| `updated_at` | **用 `seq` 就够了**，不用时间戳。理由见下 |

⚠️ **不用 `updated_at` 做增量是刻意的** —— 如果用「比某个时间戳新的」，
用户把电脑时间调回去年，云端会以为那些记录全都没变，**同步就静默失效了**。
**序号不受任何时钟影响**，这是选它的唯一理由。

### 1. `GET /api/tasks` — 拉取（增量或全量）⏳ 待实现（Day 17）

| | |
| --- | --- |
| **请求头** | `X-User-Id`（必需） |
| **查询参数** | `since`（**可选**）。不带或为空 = 全量；带了 = 只要 `seq` 比它大的 |
| **请求体** | 无 |
| **支撑页面** | 打开页面时的自动同步；同步开关的手动「拉取」按钮 |

**同一个接口，两种模式：**

| 情况 | `since` | 云端返回什么 |
| --- | --- | --- |
| **首次同步**（本地没有游标） | 不带 | 全部记录 + `cursor`（= 本页最大 seq） |
| **`since` 比本区最大 seq 还大** | 带了 | 当作**全量**，`notice` 说明「本地游标比云端还新，已重新拉取全量」。⚠️ **这通常意味着云端被重建过** |
| **`since` 不是合法游标**（负数、非整数） | 带了非法值 | ⚠️ **回 400**（不要静默当全量 —— 静默会让用户以为在增量同步，其实拉了个全量） |
| **正常增量** | `since=186` | 只要 `seq > 186` 的记录 + 新的 `cursor` |

⚠️ **第一版写的「游标失效（比如云端被重建过）云端认不出 → 当全量」是实现不了的** ——
`seq` 是全局序列，云端**没有「有效游标」这个状态**。
`since=186` 在库里 `max=500` 时是合法的；云端重建后 `max=3` 时传 186，
云端也无法判断那是「失效」还是「我这区本来就没更新」。

**契约不承诺「记住每个客户端的游标」** —— 那需要一张游标表，
与「只有 1 张表」冲突。所以只保留**唯一能检出的那种失效**：
`since > 本区 max(seq)`。其余情况按普通增量处理。

⚠️ **`notice` 只在这一种情况下非 null** —— 它是「这次其实是全量」的信号。
前端拿到非 null 的 `notice` 应在界面上说明一句（Day 20 定怎么显示）。

**成功响应 `200`：**

```jsonc
{
  "ok": true,
  "error": null,
  "data": {
    "items": [
      {
        "id": "t-mfk3x2-8a1b2c3d",
        "seq": 187,                          // ← 本版新增：变更序号
        "title": "下周一交的实验报告",
        "dueAt": "2026-10-09T18:00:00.000Z", // string | null
        "estimateMinutes": 120,              // number | null
        "importance": 5,                     // 1..5
        "status": "todo",                    // todo / doing / done
        "createdAt": "2026-10-06T02:10:00.000Z",
        "deletedAt": null,                   // string | null；非 null = 在回收站
        "purgedAt": null                     // string | null；非 null = 墓碑
      }
    ],
    "cursor": 187,      // ← 下次同步带上它。见下方定义，**不是全库最大值**
    "hasMore": false,   // ← 记录太多时置 true，前端继续拉
    "notice": null      // ← 「这次其实是全量」之类的说明；正常同步时为 null
  }
}
```

**⚠️ 三个新字段的用途，一个都不能省：**

| 字段 | 作用 | 省掉会怎样 |
| --- | --- | --- |
| `cursor` | 下次同步的 `since` 值 | 每次都要拉全量，增量同步白做了 |

🔴 **`cursor` 的精确定义 —— 这是本契约最容易被实现错的一条**

> **`cursor` = 本次响应 `items` 里最大的 `seq`**（`items` 为空时 = 请求带的 `since`，
> 首次同步且库为空时 = `0`）。
> **它是「下次 `since` 的值」，不是本区的最大 seq。**

**为什么不能写成本区最大 seq：** 分页时会跳数据。
库里 500 条时，第一页返回 `seq 1–200`，若 `cursor` 写成 `500`（全分区最大），
前端拿 500 当下次 `since` → **`seq 201–500` 永远拉不到**，
而且它不报错，就是静悄悄丢数据。

⚠️ **所以 `cursor` 可能小于库里实际的���大 seq —— 这是正常的，不是 bug。**

🔴 **`POST` 的 `cursor` 同理，必须带 `user_id` 过滤**

> `POST` 返回的 `cursor` = **本区**（`user_id` = 请求头那个值）当前最大的 `seq`。
> ⚠️ **绝不能写 `SELECT max(seq) FROM tasks`（不加 `WHERE user_id = ?`）** ——
> `seq` 是全局序列，所有用户共用。不加过滤的话，本区最大只有 188
> 却返回 90000，前端拿它当游标 → **本区此后所有记录都拉不到，且不可恢复**。
| `hasMore` | 记录多时前端继续拉 | 一次响应塞不下，超出部分静默丢失 |
| `notice` | 告诉前端「这次其实是全量」 | 前端以为拿到了全量，实际上少了数据却不自知 |

**`hasMore` 什么时候为 `true`：** 云函数有执行时长上限（体验版 900 秒），
单次返回太多条会超时。约定：**单次最多返回 200 条**，
还有更多时 `hasMore: true`，前端带 `since=<cursor>` 继续拉，直到 `hasMore: false`。

⚠️ **前端必须给这个循环设上限**：连续拉取 **超过 20 轮**仍未 `hasMore: false`
→ 停止并提示「数据量过大，已同步前一部分」。
**必须有这个上限** —— 拉取期间另一台设备若一直在加新记录，`since` 一直有新的，
循环会永远不结束（页面卡在「同步中」）。

⚠️ **任务量到 200 条才用得上**，但字段现在就要有 ——
后加字段属于改契约，不如一次写清。

⚠️ **响应里没有 `priority` / `score` / `reasons`** —— 前端拿到后自己调
`core/priority.ts` 算（取舍 1）。

🔴 **`items[]` 里三个删除相关字段的语义（一个都不能省）：**

| 字段 | 值 | 前端看到后要做的事 |
| --- | --- | --- |
| `deletedAt` | `null` | 正常任务，显示 |
| `deletedAt` | 有值、`purgedAt` 为 `null` | **在回收站里**，从队列和清单隐藏，回收站界面显示 |
| `purgedAt` | 有值 | 🔴 **墓碑 —— 从本地库真删这一条**（不是标记！） |

⚠️ **`purgedAt` 缺了整套墓碑机制就失效**：墓碑记录带着 `purgedAt: null` 回来，
前端认不出来 → 本地那条永远删不掉。而第五节要求的正是「`GET` 照常返回墓碑」，
**字段没返回 = 契约自己违反自己**。

⚠️ **`accepted[].task` 的字段与 `items[]` 完全相同**，所以那里也必须带 `purgedAt`。

⚠️ **`items` 里包含回收站和墓碑的记录**，**由前端决定显示哪些**。
理由：前端知道用户是不是正看着回收站界面，云端不知道；
而且让云端按界面筛选，等于把业务逻辑搬到后端（违反取舍 1）。

⚠️ **只有 `status` 和 `deletedAt` 决定「在不在今日队列」**：
`useTaskQueue.ts:201` 现在是 `status !== 'done'`，
接入云端后要改成 **`status !== 'done' && deletedAt === null`** ——
否则回收站里的已完成任务会漏进队列。**这条要记在第十节 B 组第 3 条。**

**错误响应（最后一列是前端怎么处理 —— 不是可选项）：**

| 码 | `error` | 什么时候 | 前端怎么处理 |
| --- | --- | --- | --- |
| 400 | `缺少 X-User-Id 请求头` | 头不存在或为空 | 整页错误态（连分区都不知道是谁的数据） |
| 400 | `X-User-Id 格式不对` | 长度 > 64 或含非法字符 | 整页错误态 |
| 400 | `since 不是合法的游标` | `since` 不是非负整数 | 提示 + 回退成全量重试一次 |
| 500 | `服务器内部错误，请稍后再试` | 数据库连不上等 | 错误提示 + 可重试 |

**没有数据不是错误**：库里没有任务时返回 `200` + `items: []` + `cursor: 0`，
**不要返回 404** ——「队列是空的」是正常状态，前端要显示空状态卡
（依据 `TasksPage.tsx` 第 106–118 行的空态分支）。

⚠️ **`cursor` 在库为空时是 `0`** —— 这样第二次同步带 `since=0`，
返回全部（因为没有一条 `seq <= 0`），**逻辑统一，不用特判「首次」**。

### 2. `POST /api/tasks` — 推送（新增 / 修改 / 移入回收站 / 墓碑 purge）⏳ 待实现（Day 18）

| | |
| --- | --- |
| **请求头** | `X-User-Id`（必需）、`Content-Type: application/json` |
| **请求体** | **一个数组**，可空、可多条（打包提交） |
| **支撑页面** | 加任务 / 完成 / 撤销 / 删除 / 导入 JSON —— 全是它 |

**⚠️ 为什么一个接口管这么多事**：因为服务端只是仓库，它不关心你「为什么」改这条。
「加一条」和「把这条改成已完成」的差别只是数组里**有没有 `id`**：
有 `id` 就是改（只更新出现过的字段），没有就是新增。
**这与取舍 1 一致 —— 后端不做业务判断。**

⚠️ **注意：新增必须带 `id`**（前端 `newId()` 早就生成了）。
「没有 `id` 就让云端生成」这条兜底已被取消，否则会造出「本地孤儿 + 云端孤儿」——
理由见下方「为什么新增必须带 id」。

**请求体（一个数组，元素按有没有 `id` 决定动作）：**

```jsonc
// 新增（没有 id）
[
  { "title": "读一遍 PRD", "dueAt": null, "estimateMinutes": null, "importance": 3 }
]

// 修改（带 id，字段只写要改的）
[
  { "id": "t-mfk3x2-8a1b2c3d", "status": "done" }
]

// 移入回收站
[
  { "id": "t-mfk3x2-8a1b2c3d", "deletedAt": "2026-10-07T09:00:00.000Z" }
]

// 从回收站恢复
[
  { "id": "t-mfk3x2-8a1b2c3d", "deletedAt": null }
]

// 彻底删除（真删，不可恢复）
[
  { "id": "t-mfk3x2-8a1b2c3d", "purge": true }
]
```

**⚠️ 四种动作的判定规则（云端照这个写，顺序不能换）：**

| 请求体里有 | 动作 | 云端怎么做 |
| --- | --- | --- |
| `purge: true`（无论还有没有别的键） | **彻底删除（留墓碑）** | **行保留**，只填 `purged_at` 时间戳。⚠️ **不是 `DELETE` 那一行** —— 理由见第五节 |
| 有 `id` + 有 `deletedAt` | 移入回收站 / 恢复 | 改 `deleted_at`，其余字段不动 |
| 有 `id`（无 `deletedAt`、无 `purge`） | **修改** | 更新请求体里**出现过的**字段 |
| **没有 `id`** | **新增** | 插入新行，`seq` 取自增序列。⚠️ 新增必须带 `id`，所以走到这里的实际是「带了非法 `id`」，已在表一里拒 |

🔴 **受保护字段：`seq` / `userId` / `createdAt` 三个永远不由请求体决定**

| 字段 | 请求体里带了怎么办 |
| --- | --- |
| **`seq`** | 🔴 **一律忽略，并在 `accepted` 里返回库里的真值。绝不能 `SET seq = 请求体.seq`** |
| **`userId`** | 一律忽略，强制用请求头带来的那个 |
| **`createdAt`** | **修改时忽略**（只在新增时采纳）；`accepted` 返回库里的真值 |

**`seq` 这条为什么是致命的**：它的值**出现在响应里**（`items[].seq`、`accepted[].seq`），
前端合并进本地后本地就有 `seq` 了。而正常写代码时很容易出现
`{ ...task, status: 'done' }` 这种展开写法 —— **请求体里就带上了旧的 `seq`**。
按「更新出现过的字段」去 `SET seq`，序号就回退了，后果是两条：

1. 同一条记录下次同步被**反复拉取**（它的 `seq` 比游标小了）；
2. 或者被别的记录超过后**再也拉不到**。

⚠️ **这条曾经是个真实的洞**：第五节写了「`seq` 由云端给」，
但没写「不可被覆盖」—— 而 `{ ...task, status: 'done' }` 这种写法
**天然会把 `seq` 一起带上**。所以现在**第五节和第六节都要写死它**：
`seq` 的**唯一赋值来源是数据库的自增序列**，且第五节用
`generated always as identity` 在数据库层也堵了一道。

⚠️ **`purge` 排在第一位判定** —— 如果一条同时带 `purge: true` 和 `status: "done"`，
**以 `purge` 为准**，不要去改别的字段（它都要被删掉了，改了也白改）。

⚠️ **「真删」与「移入回收站」的区别只有一个标志**：
`deletedAt` 填时间戳 = 还能恢复；`purge: true` = 从库里删掉、找不回来了。
所以回收站界面要**两个按钮**才完整。

⚠️ **修改时「只改出现过的字段」**：请求体里没写的字段**保持原值**。
所以移动回收站的记录要发 `{ id, deletedAt: "…" }` —— 不能发 `{ id, status: "todo" }`
顺手把状态也改了，那是两个不同的意图。

**成功响应 `201`：**

```jsonc
{
  "ok": true,
  "error": null,
  "data": {
    "cursor": 188,          // ← 推送后云端的最大 seq，前端记下来当新的游标
    "accepted": [
      { "id": "t-mfk3x2-aaa", "seq": 187, "task": { /* 落库后的完整记录 */ } },
      { "id": "t-mfk3x2-bbb", "seq": 188, "corrected": true, "task": { /* 同上 */ } }
    ],
    "rejected": []           // ← 被拒的条目（见下方「部分成功」）
  }
}
```

#### `accepted` 的字段定义

```jsonc
{
  "id": "t-mfk3x2-8a1b2c3d",
  "seq": 187,              // 🔴 云端分配的序号，必填
  "corrected": true,       // 可选：这条存进库的内容与请求不完全一致
  "task": { /* 🔴 落库后的完整记录，字段与 GET 的 items[]. 完全相同 */ }
}
```

🔴 **必须有 `seq`** —— 前端要靠它更新本地那条记录的序号，
否则下次同步会把它当成新的再拉一遍。**这是最容易漏的一步。**

🔴 **`task`（落库后的完整记录）也必须有 —— 第一版只回 `id` 和 `seq`，漏了这一项。**

漏了会怎样：用户导入一个 `importance: 99` 的文件，
云端存成 5 并回 `{ id, seq, corrected: true }`，
但前端本地那条**仍然是 99**（契约只要求用 `seq` 更新本地）。
然后：

1. 下次 `GET ?since=<seq>` —— 这条的 `seq` 已经在游标后面了，**永远拉不到修正后的 5**；
2. 本地算分用 99 → **分数算错**；
3. 导出的 JSON 仍是 99；
4. **两台设备可以永久不一致**。

所以约定：**前端用 `task` 整体覆盖本地那条**（不只是更新 `seq`）。
这样兜底修正立刻在本地生效。代价是响应体大一点（每条多一个对象），
但本来就是几百字节量级，可以接受。

⚠️ **`corrected: true` 的含义要写宽一点** —— 它是
「**这条存进库的内容与你请求的不完全一致**」，
包含四种情况：字段被夹紧 / 被改成 `null` / **被忽略** / `createdAt` 被换成服务器时间。

⚠️ **为什么要把「被忽略」也算进去**：判定表第 2 行说「有 `id` + `deletedAt` → 只改 `deleted_at`，
其余字段不动」。那如果有人发
`{ id: "x", deletedAt: "...", status: "done" }`，
`status` 会被**静默丢弃**，但 `accepted` 照样返回这一条。
如果不标记，前端会以为「完成 + 删除」都成功了 ——
**等有人从回收站恢复它，状态是旧的**。
所以收到 `corrected: true` 时，前端统一提示「有 N 条数据与你的输入不完全一致」即可。

**⚠️ 部分成功（这是本接口最容易设计错的地方）**

数组里 5 条，第 3 条不合法 —— 该全拒还是收 4 条？
**本契约定的是：能收多少收多少，拒的在 `rejected` 里说清是哪一条。**

```jsonc
{
  "ok": true,              // ⚠️ 注意：整体仍算成功，因为有用的数据收进去了
  "error": null,
  "data": {
    "cursor": 188,
    "accepted": [ /* 4 条 */ ],
    "rejected": [
      { "index": 2, "field": "title", "reason": "任务标题不能为空" }   // index 从 0 开始
    ]
  }
}
```

**为什么不全拒**：一次打包 5 条，因为第 3 条格式错就把 4 条已改好的丢掉，
用户得改完再重试。而前端只要把 `rejected` 显示出来、
成功的那 4 条照常更新本地，就能正常工作。

⚠️ **HTTP 码仍是 201**（有数据被接收），
**只有「一条都没收下」才回 400**，那时 `rejected` 里列出全部原因。

🔴 **事务边界（三步，顺序不能换）**

```
① 先校验、后写入 —— 第一遍逐条判定，把每条归入 accepted 或 rejected，
   这一遍完全不碰数据库
② accepted 为空 → 不开事务，直接 400 + rejected 全列
③ 否则在【一个事务】里写入全部 accepted 条目；事务失败 → 整体 500，
   此时 rejected 也不成立（因为什么都没写）
```

⚠️ **绝不允许「写一条提交一条」** —— 那会出现「第 3 条失败但前 2 条已提交」，
而响应却说「你原来的数据没有被改动」，前端信了、清空本地后才发现云端多了两条。

⚠️ **③ 里的 500 要说清发生了什么**：事务失败时**什么也没写进去**，
所以前端**不要重推整个数组**（虽然重推是安全的，见并发表），直接重试即可。

**校验规则分两张表 —— 一张管「拒」，一张管「修正」。第一版把它们混在一张表里，
标题却写着「`rejected[].reason` 用这些文案」，实现者会把 9 种文案全写成拒。**

#### 表一：会被**拒绝**的（进 `rejected`）

| 情况 | reason 文案 | `field` |
| --- | --- | --- |
| 顶层不是数组（含是对象、字符串、数字） | `请求体必须是一个任务数组` | `null` |
| 数组是空的 `[]` | `没有要推送的内容` | `null` |
| 数组长度 > 1000 | `一次最多推送 1000 条，请分批` | `null` |
| 元素不是对象或是 `null` | `不是有效的任务对象` | `null` |
| 新增（无 `id`） | `新增任务必须带 id` | `id` |
| 修改时目标不存在 | `找不到这个任务（编号 xxx）` | `id` |
| 修改时目标已被彻底删除（墓碑） | `这个任务已被彻底删除，不能恢复` | `id` |
| `id` 存在但格式不合规（长度或字符） | `任务编号格式不对` | `id` |
| **`title` 去空格后为空**（新增和修改**都跑**这条） | `任务标题不能为空` | `title` |
| `title` 超过 200 字 | `任务标题太长了（最多 200 字）` | `title` |
| `dueAt` 非空但**解析不出合法时间** | `截止时间格式不对` | `dueAt` |
| `deletedAt` 非空但**解析不出合法时间** | `删除时间格式不对` | `deletedAt` |

⚠️ **`title` 那条第一版只写了「新增时」，修改路径直接漏了** ——
`{ "id": "x", "title": "   " }` 会走修改分支，把空串写进库（`text not null` 拦不住空串），
界面上一张空白卡片。**`title` 是唯一不可兜底的字段** —— 夹紧或改 `null` 都没有合理语义，
只能拒。

⚠️ **`dueAt` 解析失败选择「拒」而不是「改成 `null`」**：
兜底成 `null` 会把「3 月 5 日交」静默变成「没期限」，按算法紧迫度直接变 0、
排到队列最后 —— **比报错更坏**。用户看到「截止时间格式不对」能自己改。

⚠️ **数组上限 1000**：云函数有请求体大小和执行时长上限。
导入一个 5000 条的 JSON 会撞限制然后返回 500，用户完全不知道原因。
**明确说「请分批」，比撞限制强。**

#### 表二：会被**兜底修正**的（进 `accepted`，带 `corrected: true`）

⚠️ **这张表的每一行都写着「改成什么」，不是「必须是什么」。**
（第一版的表二写的是「必须是 1–5 整数」这种校验语气，
而另一张表又写「夹到 1–5」—— 同一个字段两种处置，实现者只能猜。）

| 字段 | 什么情况 | **改成什么**（不是拒） |
| --- | --- | --- |
| `importance` | 越界（99、0、负数、非数字） | **夹到 1–5**（99→5、0→1、不是数字→3） |
| `status` | 非法值（`'deleted'`、空串） | **改成 `'todo'`** |
| `estimateMinutes` | 是小数（`1.5`） | **四舍五入成整数** |
| `estimateMinutes` | 类型不对（字符串 `'30'`、对象） | **改成 `null`** |
| `estimateMinutes` | 是 0 或负数 | **改成 `null`**（0 会被算法当成「瞬间完成」，凭空加分） |
| `dueAt` | 类型不对（不是字符串） | **改成 `null`** |
| `dueAt` | 是字符串但**解析不出时间** | ❌ **拒** —— 见表一，兜底成「没期限」比报错更坏 |
| `createdAt` | 缺失 / 类型不对 / 解析不出 | **用服务器当前时间** |
| 受保护字段 | 请求体带了 `seq` / `userId` / `createdAt`（修改时） | **忽略**，用库里的真值 |

⚠️ **注意最后两行的差别**：`dueAt`「解析不出」是**拒**，
而 `createdAt`「解析不出」是**改成当前时间** —— 看起来不一致，理由是：
`createdAt` 只是展示顺序的依据，猜错了没有后果；
`dueAt` 直接决定紧迫度和排位，猜错了会让任务静默排到最后。
#### `rejected` 的字段定义

```jsonc
{ "index": 2, "field": "title", "reason": "任务标题不能为空" }
```

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `index` | number | **在请求数组里的下标，从 0 开始**。⚠️ **请求级拒绝（表一前四行：顶层不是数组 / 空数组 / 超 1000）没有下标，约定填 `-1`** —— 前端见到 `-1` 就直接显示 `error`，不拼「第几条」 |
| `field` | string \| null | 出问题的字段名；整条有问题（如不是对象）时为 `null` |
| `reason` | string | **中文说明，一律不含「第几条」** |

🔴 **⚠️ `reason` 一律不含序号** —— 要显示「第几条」由前端用 `index + 1` 拼。

第一版把序号内插进了 `reason`（`第 3 条任务标题不能为空`），
结果前端要显示「第 3 条：xxx」时，不含序号的那些得自己拼、含序号的那些又不能拼，
两种文案风格必然混着显示。**所以序号只放在 `index` 里，`reason` 保持干净。**

⚠️ **文案不必照抄本地。** 本地 `normalizeImported` 是把 `N` 内插进文案的
（`第 ${index + 1} 条缺少有效的任务内容（title）`，`local-indexeddb.ts:160`），
但云端这个字段结构不同（多了 `index` 和 `field`），**照抄那个拼法会出错**。
云端用自己的中文文案即可。

⚠️ **「拒这一条」里的「这一条」指数组下标对应的那条，不是整个请求** ——
这是部分成功的前提。

⚠️ **会拒的共 12 种，全部列在表一**，不在这里复述。
最容易漏记的三种：`title` **超过 200 字**（不只��空才拒）、
`dueAt`/`deletedAt` **解析不出时间**、**修改目标是墓碑**。
其余都能兜底修正（表二）。

### 🔴 为什么「新增必须带 id」—— 第一版这里有个会造成垃圾数据的洞

第一版写「没有 `id` = 新增，**云端生成 id**」。但本地实现
（`local-indexeddb.ts:58`）**本来就是前端生成 id 的**，所以真实流程是：

```
1. 前端本地新建，id = xyz，已经落进本地库
2. POST，不带 id（照第一版的示例）
3. 云端生成 id = abc，返回 accepted: [{ id: "abc", seq: 187 }]
4. 前端本地那条 id = xyz  ←→  云端那条 id = abc   对不上
→ 本地出现两条一模一样的任务，孤儿 xyz 永远没有 seq
```

**所以本版取消「云端生成 id」这条兜底：新增必须由前端带 `id`。**
前端 `newId()` 已能离线生成（第五节），云端再生成一份只会造出「本地孤儿 + 云端孤儿」。

⚠️ **导入 JSON 的例外**：用户手写的 JSON 里可能没 `id`。
这种情况下**拒绝并给出明确 reason**，而不是默默造一个 ——
因为云端生成的 id 前端对不上。

### ⚠️ 并发场景：契约不给「一条都没收下」之外的保护，但有几条硬规则

| 场景 | 会发生什么 | 契约的处置 |
| --- | --- | --- |
| 修改一条**不存在**的 id | 走修改分支但目标不存在 | **拒这一条**，reason = `找不到这个任务（编号 xxx）`。前端**不删本地数据**，只在提示条说明「这条在云端已不存在，请刷新」 |
| `POST` 整个数组重推一次 | 第二次全部变成「修改」，`seq` 再前进 | ⚠️ **允许重推**（幂等性由「有 id 即修改」保证内容不变），但前端要把 `accepted` 里同一个 `id` 的 `seq` **取最大值** |
| 两台设备同时新建**同名**任务 | 两边都查不到，都插进去，**409 失效** | 接受。见下方「409 只是体验保障」 |
| 同一数组内重复 `id` | 按顺序处理，后者覆盖前者 | 允许，但 `accepted` 会返回**两个同 id 不同 seq**，前端取 `seq` 大的那个 |
| 已 purge 的 id 被离线设备重新导入 | id 复活，拿个新 seq | ⚠️ **有墓碑就能拒绝**：查 `purged_at IS NOT NULL` → 拒这一条，reason = `这个任务已被彻底删除，不能恢复` |

**409 只是体验保障，不是数据约束**：它是「先查后插」，
挡得住**同一台设备连点两次**，挡不住**跨设备同时建同名**（两边都查不到）。
⚠️ **不要为它加唯一索引** —— 加了就等于把业务判断搬进后端（违反取舍 1）。
接受「库里可能有两条同名待办」这个结果。

**⚠️ 云端做兜底修正（项目主人已拍板），与本地一致：**

| 情况 | 怎么处理 | 本地依据 |
| --- | --- | --- |
| `importance` 越界（99、0、非数字） | ✅ **夹到 1–5** | `clampImportance`，`local-indexeddb.ts:147–151` |
| `status` 是非法值（`'deleted'`） | ✅ **改成 `'todo'`** | 第 181 行 |
| ~~`id` 缺失~~ | 🚫 **取消这条兜底** | 见下方说明 |
| `createdAt` 缺失或不是合法时间 | ✅ **用服务器当前时间** | 第 182 行只判了 `typeof`，云端要补合法性校验 |
| `dueAt` / `estimateMinutes` 类型不对 | ✅ **改成 `null`** | 第 175–178 行 |
| `estimateMinutes` 是小数（`1.5`） | ✅ **四舍五入成整数** | ⚠️ 本地缺 —— `integer` 列存不了小数 |
| **元素不是对象 / `title` 为空** | ❌ **拒这一条** | 第 162–170 行 |

**错误响应：**

| 码 | `error` | 什么时候 | 前端怎么处理 |
| --- | --- | --- | --- |
| 400 | `缺少 X-User-Id 请求头` / `X-User-Id 格式不对` | 头有问题 | 整页错误态 |
| 400 | `请求体必须是一个任务数组` | 顶层不是数组 | 面板内提示 |
| 400 | `这批数据一条都没收下，你原来的数据没有被改动`（+ 顶层 `rejected`） | **一条都没收下** | 面板内提示 + **逐条显示 `rejected` 的 reason** |
| 409 | `已有一条内容相同的待办：xxx` | 见下方「重复提交」 | 面板内提示。⚠️ **409 不带 `rejected`** —— 它是整请求级失败，`error` 里已含任务标题 |
| 500 | `服务器内部错误，请稍后再试` | 数据库连不上、事务失败 | 提示 + 可重试 |

**重复提交（防重）→ `409`**

⚠️ **这条规矩只管「新增」**。`purge`、修改、`deletedAt` 变更都不判重。

| 情况 | 判不判重 | 为什么 |
| --- | --- | --- |
| 新增（无 `id`） | ✅ 判 | 「重复提交」最常发生的地方就是连点两次新建 |
| 修改（有 `id`） | ❌ 不判 | 「恢复为待办」这个很常用的动作，会把一条 done 改回 todo。若库里已有同名 todo 就拒，用户会觉得莫名其妙 |
| 移入/出回收站 | ❌ 不判 | 同上 |

**代价（要接受）**：库里可能存在两条同名且未完成的任务，前端会显示两张卡片。
**这不是 bug，是这条取舍的已知结果。**

判定规则：同一区内已存在一条 `status <> 'done'` **且 `deleted_at IS NULL`**
且 `title` **去空格后完全相同**的待办 → 拒绝。

⚠️ **判重要排除回收站和墓碑**（`deleted_at IS NULL AND purged_at IS NULL` 才参与）——
否则「删掉一条、又新建一条同样内容的」会被拒，而那是合理的。

**🔴 前端处理（不是可选项，写在这里是因为很容易做错）**

`useTaskQueue.ts:169–185` 的 `act()` 在任何失败时都 `setError(...)`，
`TasksPage.tsx:90–97` 里 `error !== ''` 会**把整页替换成「任务列表没读出来」错误页**。

后果很具体：用户在 `/tasks` 点「删除」一条已被别处删掉的任务，
云端返回 404，`act()` 抛错 → `error` 非空 → **整个页面变成错误块**，
而不是那一行提示「删除失败」。**用户填了一半的表单会整个消失。**

**Day 11 踩过同一个坑**：`useTaskQueue.ts:206–213` 的注释写明了 ——
`completeTask` 当初就是为了**不复用 `act()`** 才自己管 `busy`、失败只走底部提示条的。
**所以所有云端写操作都必须走「行内 / 底部提示条」这条路，不能图省事套 `act()`。**

**判据（写死这条，前端照做）**：
「这一件操作没成功」→ 行内/底部提示条 + 可重试，**队列不动**；
「整份数据读不出来」→ 整页错误态。两者不能混。

⚠️ 上面三行的差距合起来就是**第七节不一致 1**，这里如实标注，Day 17 一起改。

**`/api/health` 要不要校验 `X-User-Id`？→ 不要，豁免。**
它不连数据库、只回 `{ ok, service, time }`，校验分区没有意义。
第四节那两道校验只适用于 `/api/tasks` 的两个接口。**不要把规则套到 health 上**。

🔴 **⚠️ 部署后第一次请求可能返回网关原生 JSON —— 没有 `ok` 字段**

```
第一次：400 + FUNCTIONS_PARAM_INVALID 的网关错误 JSON（没有 ok / data / error）
紧接着第二次：200 + 正常 JSON
```

**前端必须以 HTTP 状态码 200 为准，不能只判 `res.ok`** ——
网关错误里根本没有 `res.ok` 这个字段，判它会得到 `undefined`，
「明明失败了但代码以为成功了」比报错更危险。

完整错误形状（含第一版没写的）：

| 情况 | 码 | 响应体 | 前端怎么处理 |
| --- | --- | --- | --- |
| 正常 | 200 | `{ "ok": true, "service": "priorknow", "time": "..." }` | 在线 |
| 非 GET（不含 `OPTIONS`） | 405 | `{ "ok": false, "data": null, "error": "method_not_allowed" }` + `Allow: GET` | ⚠️ 不合规，Day 17 一起改 |
| 未实现的路径 | 404 | `{ "ok": false, "data": null, "error": "not_found", "path": "/tasks" }` | ⚠️ `path` 是额外字段，Day 17 一起去掉 |
| `OPTIONS` | 404 | ⚠️ **本该放行 204**，Day 17 一起改 | — |
| 首次部署后的第一次请求 | 400 | 🔴 **网关原生 JSON，没有 `ok`** | ⚠️ **判状态码，不判 `res.ok`**；刷新一次重试 |
| 框架/网关层异常 | 5xx | 可能不是 JSON | 判状态码 |

⚠️ **部署后第一次请求可能返回 400，立刻第二次就正常** —— 网关路由生效有短暂窗口。
**判断成功要看「连续两次都 200」，别只试一次。**
（这个坑我栽过：单测一次看到 400，差点把「health 是保留路径」这个**错误结论**写进代码注释。）

### 5. ❌ 明确不做的接口（第一版有，这版删掉，理由记下来）

| 第一版的接口 | 为什么删 |
| --- | --- |
| `GET /api/tasks/:id` 读单条 | 数据已整份在本地，**问云端单条毫无意义** |
| `PATCH /api/tasks/:id` 改一条 | 合并进 `POST /api/tasks`（带 `id` 就是改） |
| `DELETE /api/tasks/:id` 删一条 | 合并进 `POST /api/tasks`（`deletedAt` / `purge`） |

实际上**会破坏增量同步的前提**。所以本版不做。

如果将来真要做「导入 JSON 覆盖全部」，正确做法是：
**先 `GET` 拉全量 → 前端合并 → 用 `POST` 逐条推**，让 `seq` 正常前进。

### 不一致 2：`userId` 现在只是分区，不是身份（**Day 23 之后会改善，但今天仍存在**）

取舍 2 已经写明：`X-User-Id` 不校验、不认证，清缓存即换区。
契约在此重申，因为**这不是安全边界**，文档写清楚才不会被误当成「已经做了用户隔离」。

**未来已定会改善**（取舍 9）：Day 22 之后做登录，用 CloudBase 内置认证，
登录后 `user_id` 换成认证系统的 uid —— **同一账号的多台设备才会看到同一批数据**。

⚠️ **但即使做了登录，`X-User-Id` 这个请求头本身仍然不认证** ——
服务端的读法还是「请求头里写什么就取什么」，
真正的身份校验发生在**登录系统**那一层（前端拿到的登录态 uid 才是真的）。
⚠️ **不要以为有了登录，`X-User-Id` 就变成可信的了** ——
任何人都能伪造这个头去读别人的区。**这不是安全边界，这是分区键。**

### 易误实现点 1：默认开启同步，但**用户同意之前不能传**

取舍 8 定了「登录后默认开启自动同步」。但**默认开启 ≠ 自动上传** ——
第一次要弹一次询问，用户明确选了「开启」才发第一个请求。

⚠️ 登记这条**不是说要改什么**（取舍 8 已经写死了，没有可改的），
而是因为它极易实现成「不问就传」：
代码里把「默认值 true」写成「初始化时直接开始同步」只差一行，
但**那一行就是「数据离开本机前有没有问过用户」的边界**。

### 易误实现点 2：墓碑 90 天后自动清理 → **离线超 90 天的设备会看到幽灵任务**

第五节已规定 90 天清理，也已写明后果：
离线超过 90 天的设备收不到墓碑，它本地那条被 purge 的任务会留着，
再次改动时会被拒（`rejected`：`这个任务已被彻底删除，不能恢复`）。

**如实登记，不悄悄抹平** —— 这是「自动清理」与「删除必须能同步」之间的
**真实取舍**，不是 bug，也不是待修的不一致。
⚠️ **不要看见「幽灵任务」就去把它当 bug 修掉** ——
`purged_at` 立刻删掉或延长保留期都是在破坏删除同步机制。
**两个都要，选了 90 天就是接受这个后果。**
