# 云函数分层说明（Day 19 重构）

> 这份文档解释一件事：**为什么把原来 882 行的 `index.js` 拆成 7 个文件**，
> 以及拆完之后「加一个新接口」要做的事从 5 步变成了 3 步。
>
> 重构前后**接口路径、字段名、返回形状、状态码一个字都没改** ——
> 这份文档只描述代码放在哪，不描述功能变化。

**依赖只能单向**：入口 → 业务 → 数据。

数据层**不认识**上面两层：`data/tasksRepository.js` 里没有 `reply`、没有请求头、
没有状态码 —— 它不知道调用它的是 HTTP 云函数还是别的东西。
这条约束是真拆开了和假拆开了的分界线。

## 二、拆之前长什么样（为什么非拆不可）

Day 17–18 为了先跑通，查询是直接写在接口函数里的。当时「乱但能跑」，
问题在第二天开始显现：

| 症状 | 具体表现 |
|---|---|
| 同一个条件写了很多遍 | `user_id` 这个过滤条件在 **6 个地方**各写了一次 |
| 一个函数干三件事 | `handlePostTasks` 同时管校验、查库、拼响应，260 行 |
| 改一处要翻整份文件 | 想知道「谁碰了 tasks 表」，只能全文搜索 `from('tasks')` |
| 复用时靠复制 | 再来一个 PATCH，又得把 `db.from(...).eq('user_id', ...)` 抄一遍 |

**最先会咬人的是第一条**：Day 23 接入登录后，`user_id` 不再从请求头拿，
而是从登录态拿 —— 那时要改 6 处；漏掉一处，用户就会看到别人的数据。

拆完之后：**改 1 处**（数据层），上层一行不用动。

## 三、六个文件各自负责什么

| 文件 | 层 | 职责 | 不该出现的东西 |
|---|---|---|---|
| `index.js` | 入口 | 路由分派、OPTIONS 预检、405/404 | 任何查询、任何校验规则 |
| `http/reply.js` | 入口 | 拼 `{ok,data,error}`、CORS 头、读头 | 业务判断 |
| `tasks/handlers.js` | 业务 | 两个接口的流程编排 | `db.from(...)` |
| `tasks/validate.js` | 业务 | `judgeOne` 纯校验 + 校验用常量 | 数据库、HTTP |
| `tasks/mapper.js` | 业务 | snake_case ↔ camelCase、时间归一化 | 数据库、HTTP |
| `data/db.js` | 数据 | `getDb` / `queryAll` | 表名、字段名 |
| `data/tasksRepository.js` | 数据 | tasks 表全部查询 | HTTP、状态码、请求头 |

**一个判断标准**（以后自己检查用）：随便打开一个文件，
如果里面既有 `req.headers` 又有 `from('tasks')`，那就是还没拆干净。

## 四、为什么「分批查库」跟着数据层走

原来判重和查现状这两个地方，为了绕开 PostgREST 的 URL 长度限制，
各自写了一遍「每 100 个一批」的循环：

```js
for (const batch of chunk(ids, IN_BATCH)) { ... }
```

拆完之后这个循环进了 `data/tasksRepository.js` 的 `findByIds()` 和
`findDuplicateTitles()` 内部。理由是：**「一次能查多少个 id」是数据库的限制，
不是业务规则**。业务层只该说「把这 20 个 id 的现状给我」，不该知道要分几批。

→ 所以 `IN_BATCH` 这个常量也从校验常量堆里挪到了数据层。

## 五、怎么证明「行为真的一行没改」

重构最危险的地方不是拆错，是**拆完看起来正常但某个分支悄悄变了**。
这次的证据有三层，缺一层都不算数：

| 层 | 做法 | 结果 |
|---|---|---|
| ① 代码级 | 7 个文件逐个 `node --check` | 全部通过 |
| ② 逻辑级 | 本机跑 `verify-rdb-tasks.cjs`（42 项）+ `verify-post-tasks.cjs`（50 项） | **92/92 通过** |
| ③ 真实环境 | 部署后打公网地址，逐个接口重调一遍 | 见下 |

🔴 **第 ② 层为什么可信**：那两个脚本用的是**假 SDK**（把 `@cloudbase/node-sdk`
塞进 `require.cache`），验的是**云函数的真代码**，不是另写一份模拟实现。
而且它们是 `require('index.js')` 之后调 `main()` —— 重构改了文件位置，
脚本一行没改还能跑通，本身就是「对外行为没变」的证据。

**如果重构时顺手把测试也改了，就等于把考题一起改了，那 92 项全绿也没意义。**

第 ③ 层的清单（每条都要对状态码和响应形状）：

| 请求 | 期望 |
|---|---|
| `GET /api/health` | 200，`{ok,data:{service,time},error:null}` |
| `GET /api/tasks` | 200，7 条种子数据，`cursor=7` |
| `GET /api/tasks?since=7` | 200，空 items + notice（边界分支）|
| `POST /api/tasks`（新 id）| 201，`accepted` 一条，`seq` 变大 |
| `POST /api/tasks`（同 id 再推）| 201，库里不多行，`seq` 再变大 |
| `POST /api/tasks`（缺 title）| 400，`rejected[0].field = 'title'` |
| `POST /api/tasks`（不同 id 同标题）| 409 |
| `PATCH /api/tasks` | ~~405 + `Allow` 头~~ → **Day 22 起是 404**，并提示改写成 `/tasks/{id}` |
| `OPTIONS /api/tasks` | 204 + 放行 `X-User-Id` |

## 六、以后加一个新接口（比如 Day 22 的 PATCH）要做几步

| 步骤 | 改哪个文件 |
|---|---|
| 1. 写校验（如果需要新的规则）| `tasks/validate.js` |
| 2. 写查询（如果需要读/写数据）| `data/tasksRepository.js` |
| 3. 写流程编排 | `tasks/handlers.js` |
| 4. 挂路由 | `index.js` |

**不需要动的**：`http/reply.js`、`data/db.js`、`tasks/mapper.js`。
响应壳和连接逻辑都已经就位，直接拿来用。

## 七、Day 23 追加：两处新的公共位置

### 1. `messages.js` —— 平级的公共叶子模块（新增）

```
cloudfunctions/api-health/
├── index.js        入口层
├── messages.js     ← 新增。固定文案常量，谁也不依赖
├── http/reply.js   入口层
├── tasks/…         业务层
└── data/…          数据层
```

为什么它是**根目录下的独立文件**，而不是塞进 `http/` 或 `tasks/`：

- 入口层（`index.js`）和业务层（`tasks/handlers.js`）**都要**用它；
- 放进 `tasks/` → 入口层依赖业务层，违反「入口 → 业务 → 数据」；
- 放进 `http/` → 业务层依赖入口层，同样违反；
- 放根目录 → 两边都只是**往下拿**，它自己谁都不认识，单向依赖保住了。

一句话判据：**一个模块被两个不同层同时需要时，它应该落在这两层的公共下界，而不是其中一层的内部。**

现在里面只有一条常量 `INTERNAL_ERROR`（5xx 的唯一说法），原先是三处硬编码。
拆出来不是为了省几个字，是为了**防止三处各说各话** —— 改了一处忘另一处，
用户就会看到两句话描述同一件事。

### 2. 入口层的最后一道网（`index.js` 的 `exports.main`）

`exports.main` 现在只做一件事：`try { return await route(...) } catch { … }`，
异常交给原来的 `route()`。

它不是重复兜底 —— 业务层的 `try/catch` 只覆盖「进了 handler 之后」的代码，
而**路由匹配、读请求头、拼响应、OPTIONS 分支**这些地方原来没有任何兜底。
一旦在那里抛出，异常会直接交给运行时，回给浏览器的就不是我们的响应壳了。

代价是那个兜底分支平时跑不到 —— 所以专门有 `verify-day23-500-shell.cjs`
用一个会抛错的 `httpContext` getter 把它逼出来（39 项）。
